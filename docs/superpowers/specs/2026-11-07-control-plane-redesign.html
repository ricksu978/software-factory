Control plane redesign

The control plane splits into four services: a BFF that serves the dashboard and signs people in, an orchestrator API that owns every control action, a cell API that only cells can reach, and a worker that runs the background jobs. They share one Postgres and talk through it.

This replaces the single always-on control plane in the 2026-11-05 design: its architecture diagram, its dashboard sign-in and its control plane row in the Azure table. The item lifecycle, SOP, cells, safety rules and data model stay as they are, except where §08 here changes them.

01Problem

Today one Node process on one port serves the cell API, the model gateway, GitHub's webhook and the dashboard, and runs the scheduler tick and the board poller (src/main.ts:1). Three problems come from that.

  • Sign-in. Cells reach the same port, so the dashboard can't sit behind an ordinary sign-in. It prints a new one-time link at each start instead (src/http/auth.ts:45), so every restart signs the owner out.
  • No API boundary. Dashboard handlers call the control functions in-process and check roles themselves (src/http/routes.ts:317, :341, :369). A CLI or chat bot would have to copy that code.
  • One event loop for everything. A slow dashboard query, a busy cell and the scheduler tick compete for the same process, and deploying any one of them restarts all of them.

04Sign-in and sessions

The BFF is the only OIDC client. The browser never sees a token. Yours

  1. The SPA calls /bff/v1/*. Without a valid session the BFF answers 401, and the SPA sends the browser to /auth/login.
  2. The BFF starts the authorization code flow with PKCE at the configured issuer, found through OIDC discovery. State, nonce and the PKCE verifier go in a short-lived HttpOnly cookie.
  3. The provider redirects to /auth/callback. The BFF exchanges the code, checks the ID token, and refuses the sign-in if the access token isn't a JWT.
  4. The BFF writes a session row and sets the session cookie: a random id, HttpOnly, SameSite=Strict, Path=/, plus Secure in Azure.
  5. On each /bff/v1/* call, the BFF loads the session, refreshes the access token when it expires within 60 seconds, and forwards the call to the API with Authorization: Bearer.
  6. /auth/logout deletes the session row and clears the cookie.

Provider configuration

Any OIDC provider works, through the same settings. Keycloak is the local one. Yours

The design assumes every provider issues JWT access tokens carrying the API's audience. Yours Not every provider does. Google's access tokens are opaque (RabbitMQ's Google notes). So both services fail fast: the API refuses to start when discovery has no jwks_uri, and the BFF refuses a sign-in whose access token isn't a JWT. Keycloak adds an audience through an Audience protocol mapper on a client scope (Keycloak protocol mappers).

Sessions

  • Postgres, not memory. A restart of the BFF signs nobody out. Yours
  • Expiry. Seven days idle, 30 days absolute. My call
  • Cross-site requests. Every state-changing /bff/* call must carry an Origin equal to the BFF's own, as today's dashboard requires (src/http/routes.ts:292).
  • Losing access. The API reads the user's role on every request, as today's dashboard does (src/http/routes.ts:286). So removing someone ends their access on their next request, even with a live session.

Exactly one worker

Two workers would launch every cell twice. The worker holds a session-level Postgres advisory lock on its own connection, taken with pg_try_advisory_lock, which returns false at once when another session holds it. Postgres releases the lock when the session ends, even on an unclean disconnect (advisory lock functions), so a crashed worker never blocks its replacement. My call

Events in place of hooks

Today a transition's hooks run after commit, in whichever process made the transition (src/store/items.ts:45), and nothing retries a hook that fails (src/control/board.ts:39). Every transition and override already writes an event in the same transaction as the state change (src/store/items.ts:44, :65). So the worker reads events after a stored cursor, acts on each one, then moves the cursor. A crash means the event is handled again, so every effect must be safe to repeat. Board comments already carry an idempotency key (src/control/board.ts:56). The other board calls need checking. Open

Health

The worker records a heartbeat each tick. The API returns it with the floor, and the SPA shows "scheduler not ticking" when it goes stale, so a stopped worker doesn't look like a quiet factory. My call

11Testing

  • Unit. node:test per service, as today.
  • API end to end. Tests get a real token from Keycloak's e2e client by direct grant, with no browser. Direct access grants have to be enabled on that client (Keycloak securing apps), and only that client.
  • BDD. The sign-in scenarios in features/pbi-19-dashboard.feature and features/pbi-89-dashboard-wiring.feature are rewritten for OIDC. Their steps today read the dev token (features/steps/pbi-89.steps.ts:101).
  • UI end to end. Deferred. Add a browser driver when a flow only the UI can show needs a test.
