Control plane redesign

The control plane splits into four services: a BFF that serves the dashboard and signs people in, an orchestrator API that owns every control action, a cell API that only cells can reach, and a worker that runs the background jobs. They share one Postgres and talk through it.

This replaces the single always-on control plane in the 2026-11-05 design: its architecture diagram, its dashboard sign-in and its control plane row in the Azure table. It would also replace that design's decision that sign-in accepts Google, personal Microsoft and work or school Microsoft accounts (2026-11-05 decision log), once you confirm that in §14. Under the redesign, which accounts can sign in depends on the configured provider (§04). The item lifecycle, SOP, cells, safety rules and data model stay as they are, except where §08 here changes them.

Yours you decided it My call a default you can override Open not checked yet, see §13

01Problem

Today one Node process on one port serves the cell API, the model gateway, GitHub's webhook and the dashboard, and runs the scheduler tick and the board poller (src/main.ts:1). Three problems come from that.

  • Sign-in. Cells reach the same port, so the dashboard can't sit behind an ordinary sign-in. It prints a new one-time link at each start instead (src/http/auth.ts:45), so every restart signs the owner out.
  • No API boundary. Dashboard handlers call the control functions in-process and check roles themselves (src/http/routes.ts:317, :341, :369). A CLI or chat bot would have to copy that code.
  • One event loop for everything. A slow dashboard query, a busy cell and the scheduler tick compete for the same process, and deploying any one of them restarts all of them.

04Sign-in and sessions

The BFF is the only OIDC client. The browser never sees a token. Yours

  1. The SPA calls /bff/v1/*. Without a valid session the BFF answers 401, and the SPA sends the browser to /auth/login.
  2. The BFF starts the authorization code flow with PKCE at the configured issuer, found through OIDC discovery. State, nonce and the PKCE verifier go in a short-lived HttpOnly cookie with SameSite=Lax, so it survives the provider's redirect back, which is a cross-site navigation.
  3. The provider redirects to /auth/callback. The BFF exchanges the code, checks the ID token, and refuses the sign-in if the access token isn't a JWT.
  4. The BFF writes a session row holding the token's issuer and subject, and sets the session cookie: a random id, HttpOnly, SameSite=Strict, Path=/, plus Secure in Azure.
  5. On each /bff/v1/* call, the BFF loads the session, refreshes the access token when it expires within 60 seconds, and forwards the call to the API with Authorization: Bearer. The API resolves the user from the token. If the person isn't in user, it answers 403 and the SPA shows a no-access page, as today's dashboard does (src/http/routes.ts:287).
  6. /auth/logout deletes the session row and clears the cookie.

Provider configuration

Any OIDC provider works, through the same settings. Keycloak is the local one. Yours

The design assumes every provider issues JWT access tokens carrying the API's audience. Yours Not every provider does. Google's access tokens are opaque (RabbitMQ's Google notes). So both services fail fast: the API refuses to start when discovery has no jwks_uri, and the BFF refuses a sign-in whose access token isn't a JWT. Keycloak adds an audience through an Audience protocol mapper on a client scope (Keycloak protocol mappers).

Because of that assumption, Google accounts can't sign in through Google directly. Letting Google and Microsoft accounts in through one issuer needs a broker in front of them, such as Keycloak, which supports both as identity providers (Keycloak server admin guide). Picking the Azure broker is open (§13).

Sessions

  • Postgres, not memory. A restart of the BFF signs nobody out. Yours
  • Expiry. Seven days idle, 30 days absolute. My call
  • Cross-site requests. Every state-changing /bff/* call must carry an Origin equal to the BFF's own, as today's dashboard requires (src/http/routes.ts:292).
  • Losing access. The API reads the user's role on every request, as today's dashboard does (src/http/routes.ts:286). So removing someone ends their access on their next request, even with a live session. The live event stream is one long request, so the API ends each stream after five minutes, and the browser's reconnect goes through the same check. My call

Exactly one worker

Two workers wouldn't claim the same item, because claimNext skips locked rows (src/store/items.ts:104). But each would claim its own, which overshoots the WIP limit, and each would poll and judge every item. So the worker holds a session-level Postgres advisory lock on its own connection, taken with pg_try_advisory_lock, which returns false at once when another session holds it. Postgres releases the lock when the session ends, even on an unclean disconnect (advisory lock functions). My call

  • Lost lock. If the lock's connection errors or closes, the worker stops ticking and exits, and the platform restarts it. It never keeps working through its pool without the lock.
  • Standby. A worker that can't take the lock does nothing and retries every 15 seconds. That covers a revision swap, where the old and new worker overlap.

An outbox in place of hooks

Today a transition's hooks run after commit, in whichever process made the transition (src/store/items.ts:45), and nothing retries a hook that fails (src/control/board.ts:39). Every transition and override already writes an event in the same transaction as the state change (src/store/items.ts:44, :65). A cursor over that event table can't work: event.id is a random uuid and event.at is taken at insert, not at commit (db/migrations/001_init.sql:140), so a cursor would skip events from transactions that commit late. My call

  1. In the same transaction as the event, transitionItem, overrideItem, decisions and webhook intake insert one outbox row per consumer, with a bigserial sequence.
  2. The worker takes the oldest due rows for each consumer with for update skip locked, handles each one, and deletes it once every effect has succeeded.
  3. A handler throws when any effect fails. Today's mirror logs each failure and carries on (src/control/board.ts:41), so that changes. The row stays, its attempt count goes up, and it's retried with backoff, doubling from 30 seconds up to 30 minutes.
  4. A failing row holds back only the later rows for the same item and consumer, so one bad item never stalls the others.
  5. After 10 attempts the row is marked failed and set aside. It's logged and counted on the floor next to the heartbeat, so someone sees it.
  6. A row from a transaction that hasn't committed is invisible until it commits. It's never skipped, so nothing is lost.
  7. Transitions on one item take that item's row lock (src/store/items.ts:34), so one item's rows are numbered in commit order and handled in that order.
  8. The outbox starts empty on the first deploy, so history isn't replayed onto old items.

A crash between an effect and the delete means the row is handled again, so every effect must be safe to repeat. Every idempotency key comes from the event id, and every text comes from the event's payload, never from state read when the row is handled. Two keys change for this. The decision announcement's key includes Date.now() (src/control/decisions.ts:83), and the waiting comment's key and question text are read from the item's current state (src/control/board.ts:26, :56). Whether setStatus, claim, release, close and linkPr are safe to repeat needs checking. Open
