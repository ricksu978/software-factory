Software Factory

A cloud service that never stops. It watches one or more Scrum backlogs, takes Product Backlog Items one at a time or several in parallel, and runs each through a written SOP with Claude agents. Every item that meets the Definition of Done ships as an Increment.

Yours you asked for it My call a default you can override All decisions logged in §14

01Intent

Refined, ordered backlog items sit waiting for a developer to free up. The factory takes the routine ones, so people spend their time refining the backlog and reviewing and accepting work.

Throughput and quality are measured together. The factory is working when its Increments pass the same Definition of Done as human work, cost per item is one the team accepts, and people spend less time per item than they would building it themselves.

02Scope

Goals

  • Runs in the cloud 24/7. Yours
  • A private dashboard for reporting and monitoring. Yours
  • Watches backlogs, picks PBIs, runs the SOP, delivers an Increment. Yours
  • Concurrency is a fixed number or comes from past cadence. Yours
  • Any orchestration decision can be overridden from the dashboard. Yours
  • BDD and TDD by default. Behaviour is written in Gherkin at planning, and every test fails before the code that makes it pass. Yours
  • PRs are tiered Low, Medium or High risk and need 0, 1 or 2 human approvals, the model Anthropic's Claude Code team uses. Yours
  • Every run is auditable, down to the SOP version, model and cost. My call

Non-goals

  • Writing or ordering the backlog. The Product Owner keeps that. My call
  • Running Sprint events. The factory feeds Sprint Review and nothing more. My call
  • Production deploys in v1. The factory stops where your Definition of Done stops, staging at most. My call

Anti-goals

The factory has failed, even if it runs, when it:

  • merges work a human reviewer would have rejected,
  • touches items or repos nobody gave it,
  • adds to human review load,
  • spends money it can't account for item by item.

03Scrum terms the factory uses

The factory follows the 2020 Scrum Guide. Two passages set its delivery rule.

"The moment a Product Backlog item meets the Definition of Done, an Increment is born."Scrum Guide 2020, Commitment: Definition of Done, scrumguides.org
"Multiple Increments may be created within a Sprint. ... However, an Increment may be delivered to stakeholders prior to the end of the Sprint."Scrum Guide 2020, Increment

So the factory never holds work for the end of a Sprint. Each PBI that passes the DoD gate becomes an Increment right then. At Sprint Review, the team presents the sum of that Sprint's Increments.

GitHub ships first. Azure DevOps and other systems plug in later without changes to the scheduler, SOP runner or dashboard. Yours The core talks to two interfaces, one for backlogs and one for repo hosts. They're separate because a team can keep its backlog in one system and its code in another.

05PBI lifecycle

Every item moves through one state machine, and its state lives only in the state store. The backlog item mirrors it through a status field and comments, so people who never open the dashboard can still follow along.

stateDiagram-v2
  [*] --> Eligible
  Eligible --> NotReady: readiness check fails
  NotReady --> Eligible: item edited, or a readiness input changed
  Eligible --> Queued: ready
  Queued --> InProgress: WIP slot + claim

  SignOff --> InProgress: approved, or changes asked
  InProgress --> NeedsInput: agent blocked

  InReview --> Accepted: approvals met, or merged by a person

  InProgress --> Failed: retry budget spent
  NeedsInput --> Abandoned: no answer in 5 days
  SignOff --> Abandoned: no answer in 5 days
  InProgress --> Queued: lease expired, or a usage limit
  Accepted --> Failed: DoD fails after merge, bug PBI filed
  Failed --> Queued: human re-queues
  Abandoned --> Queued: re-queued, or a late answer

  Abandoned --> NeedsInput: re-queued, question still open

  • Claiming. The scheduler takes a lease on the item and the cell renews it every 60 seconds. After 5 missed renewals the lease expires and the item goes back to Queued, branch intact. Each lease carries a generation number that goes up on every claim, and again whenever the item leaves InProgress. A cell checks its generation before every push, comment and state write, and exits once it no longer holds the lease. It also stops itself after 3 minutes of failed renewals, before the 5-minute expiry, so an old cell is gone before a new one starts. My call
  • Needs input. The agent posts its question as a comment on the item and in the dashboard. You answer in either place. On the item, a comment that starts with /answer counts, and only when its GitHub login maps to a user on the dashboard's allowlist, so ordinary discussion on the item is never taken as an answer. The item gives up its WIP slot while it waits, so one stuck item can't stall the line. The factory reminds on the item and on Floor at day 2 and day 4, and after 5 days with no answer the item is Abandoned. My call
  • Sign-off. Scenarios wait for the Product Owner the same way. On the item, a product owner comments /approve, or /changes followed by a note. The sign-off view lists each acceptance criterion beside the scenarios tagged with it and flags any criterion with none. Reminders and the 5-day limit work as for Needs input.
  • Waiting on people. An item that waits for a person holds no slot, so the WIP number alone doesn't bound the work landing on people. In every concurrency mode the scheduler starts no new item while the items waiting on a person reach review_capacity, default 3. Those are items whose question or sign-off is still unanswered, plus factory PRs waiting on a reviewer. An item whose answer has arrived can always resume, so answering never stalls the line. Floor shows the count beside the WIP number. My call
  • Coming back. A Failed or Abandoned item returns to Queued when an operator re-queues it, and an Abandoned item also returns when its question gets a late answer. It resumes at its last checkpoint, except when its PR has already merged; then it starts a new run on a new branch. When a person closed its PR without merging, it resumes at Open PR, which opens a fresh PR from the same branch. A merge or a close that happens while the item is In progress, during address for example, counts the same way: the webhook, or the poller when no webhook came, moves the item to Accepted or withdraws it. A cell that reaches Open PR on a branch whose PR has already merged opens nothing and ends the stage as failed, naming the merged PR. An item re-queued while its question is still open goes back to waiting, with a fresh 5-day clock.
  • Backlog changes. The watcher compares each item in the factory with the version the run started from. When the acceptance criteria change, the factory comments on the item, closes its PR if one is open, and starts a new run from Understand on a new branch from the base, which leads to a new sign-off. A fresh branch matters because the old one already holds code, so new scenarios would pass before Red. When the opt-in label is removed or the item is closed, the factory stops the run, frees the slot, closes the factory's PR with a comment, keeps the branch and moves the item to Abandoned. Both moves are logged as system events. My call
  • Board status. The factory owns the status field of the items it holds. The project's built-in workflows that set status, such as item closed and pull request merged, stay off. A factory PR references its item with Refs #n, so a merge doesn't close it, and the factory closes the item when it reaches Done. Yours
  • Assignment. While an item is in the factory, it's assigned to the factory's bot account, so no person picks it up at the same time. Where the git host can't assign the bot, a factory:in-progress label does the same job.
  • Overrides. A dashboard override can move an item along paths the diagram doesn't draw, such as holding a queued item or sending a reviewed one back to Specify. Each such move is logged as an override event. See §8.

BDD rules

  • Traceability. Every acceptance criterion gets a tag, and at least one scenario carries it. Stage 2 fails on any criterion without a scenario. Each feature file also carries its PBI's tag, such as @pbi-482. Red and the traceability check look only at that PBI's scenarios, and the lock covers only its files. Green runs the whole suite, so earlier Increments' scenarios keep guarding against regressions.
  • Business language. Scenarios describe behaviour the Product Owner can read, with no selectors, SQL or class names. Implementation detail belongs in step definitions. This rule, and a Rule per business rule with scenarios for the happy path, edge cases and failures, make up the default scenarios.md. A repo can replace them. The other rules in this list belong to the engine.
  • The lock. At sign-off the factory records the commit of the feature files. After that the build may add step definitions and unit tests, but it may not edit, skip or tag out a locked scenario. Every later gate compares the feature files against the lock. A scenario that turns out wrong goes back to Specify and through sign-off again. My call
  • Red proof. A scenario that passes before any behaviour exists tests nothing new, or its steps don't assert. Stage 4 reports it as a finding and doesn't proceed. A scenario tagged @regression is the exception. It restates behaviour that already holds, such as "every existing test still passes", so Red needs it green instead, and a red or crashed one is the finding. An item whose every scenario is @regression fails Red, because Red then proves nothing. Green treats @regression like any other scenario.
  • Runners. Each repo uses its existing Gherkin runner. Cucumber lists official implementations for JavaScript, Java, Kotlin, Ruby, Scala and C++ (cucumber.io). For .NET, Reqnroll is "a Cucumber-style BDD test automation framework" built as "a reboot of the SpecFlow project" (reqnroll.net). A repo with no runner gets one in its first factory PBI, and its commands go in the repo config. My call
  • Reading runner results. Every runner writes a Cucumber Messages report, the format the Cucumber project calls "the preferred standard" (cucumber/messages). Reqnroll writes it from v3.0 (Reqnroll formatters). The factory reads step statuses from that report and never parses console output. A scenario counts as red only when its first non-passing step is FAILED and is an Outcome step, a Then. Any UNDEFINED, PENDING or AMBIGUOUS step, a failed hook, or a failure in a Given or When counts as a crash. A missing or empty report gives no verdicts, so Red fails every expected scenario as not run, and Green fails too (schema). My call

Risk tiers

Stage 9 copies the approval model from "How the Claude Code team does code review" (claude.dev, 2026-10-15). The table is theirs, word for word. Yours The approvals column is the engine's. The examples column is the default risk.md, and a repo replaces it with its own examples of what each tier means there.

RiskExamplesHuman approvals
LowDocs, copy, internal-only features, additive changes behind a flagNone required once automated review and security checks are green
MediumOrdinary product changes, and changes to sensitive areas such as caching, the auto-updater, or system promptsOne person
HighThe highest-risk code, plus a small set of paths that always need two peopleTwo people
  • The change sets the tier. A classifier reads the diff and the repo's risk.md, and picks the tier, whoever or whatever wrote it. A second pass asks whether this particular change needs a person even when its tier says no. Path rules run first, and no risk.md can lower them. CI workflow files, the repo's sensitive_paths, anything under .factory/ or .claude/, and AGENTS.md or CLAUDE.md anywhere in the repo always need at least one person. Those files steer the factory's own agents, so a change to them must never pass at Low. The classifier uses the coding model, because a wrong Low lets code skip review. My call for the model.
  • Agents never fill a human slot. Approvals from self-reviewer, pr-reviewer or any other agent don't count toward the number. A Low PR merges without a person only once automated review and the repo's security checks are green.
  • Trusted authors. In the source, only authors on a repo's trusted list get the lighter paths, and everyone else needs a second person. The factory's bot account is treated as an author like any other. It gets the table's numbers only in repos whose owners add it to the trusted list. Elsewhere a factory PR needs one more person than its tier says, up to two. Yours for per-repo trust, My call on how to read "a second person".
  • No directing person. In the source, whoever prompted an agent counts as one of its reviewers. A factory item has no such person, so every required approval comes from a reviewer.
  • One commit per approval. An approval covers the commit it was given on. When the factory pushes after an approval, for example pr-addresser fixing a thread or resolving a conflict, the approval no longer counts and the factory asks again. One exception keeps stage 8's base syncs from adding review load. An approval still counts when every commit since it is a merge of the base that leaves the PR's diff unchanged. The factory checks that by comparing the patch-id of git diff base...head at the approved commit and at the new head.
  • Enforcement. Low needs zero approvals, so the git host can't require a fixed review count. The factory posts a required status check, risk-approval, that turns green only when the tier's approvals are met on the head commit. Branch protection requires that check with the factory's GitHub App as its expected source. GitHub then blocks the merge "if the status is set by any other person or integration" (GitHub). The App has no admin rights and is on no bypass list, so it can't change the protection that checks it.
  • Review requests. When the PR opens, the factory requests reviewers from the repo's CODEOWNERS file, or from reviewers in .factory/config.yml when the repo has no CODEOWNERS. Floor shows how long each PR has waited. My call
  • Visible tier. The PR body and the dashboard show the tier and the classifier's reasons, so a reviewer can challenge them. An operator can raise a tier. Nothing lowers one, overrides included.

The factory is generic. Its engine owns the mechanics: states, leases, the scenario lock, red proof, approval counting and path floors. Every judgement about what is good enough lives in plain markdown in the repo's .factory/ folder, in the team's own words. The factory reads each file at the run's pinned commit and hands it to the agent or model that makes that judgement. Yours

The factory numbers the criteria and reports on each as passed, failed or, in dod.md only, left for the person who merges, with a reason. A missing answer counts as a fail. scenarios.md and risk.md are guidance. The agent that writes scenarios, or picks a tier, reads the whole file, and nothing scores them line by line. Prose in any file is guidance. My call
  • Who judges. In dor.md the readiness model judges each line against the item text and its readiness fields. In pr-review.md the reviewer judges each line against the diff, and stage 6 passes only when it reports APPROVED, or OPEN: 0, which says the same, and every line passed. In dod.md an agent in the cell judges each line against the diff, the scenario report and CI, before the PR opens. A line it can't decide before merge, such as "deployed to staging", it marks for the person who merges. That line goes to the PR checklist unticked and never fails the item. A person ticks the checklist at merge. Self-review and review fixes can push code after that check, so the cell checks dod.md again before the PR opens or returns to review whenever the branch head has moved, and the checklist names the commit it was checked at.
  • Commands. Only dod.md may hold a line with run: <command> in backticks. The cell runs it in the repo checkout before the PR opens, with a 15-minute limit and an env holding only PATH, HOME, CI=true, the proxy variables, and FACTORY_PG_BIN when the image sets it, so a test can start its own Postgres. The line passes only when the command exits 0. That env keeps the cell's tokens out of the command's variables, but the command runs as the cell's own user. So it has the same reach as the repo's test command and as the agent that wrote the code, and no more. A run: line in any other file makes that file invalid, and the factory reports why. My call
  • Defaults. The factory ships each default under policy/ in its own repo, inside both its images. A repo file replaces the default whole and never merges with it, so what a team reads is what runs. A file falls back to its default only when the repo truly lacks it. A failed read stops that step and retries, because silently swapping a team's stricter file for the default would be worse. Run detail says which files came from the repo and which were defaults. My call
  • What stays in the engine. This is the one list of rules no policy file can weaken. A file can add criteria on top.
    • An item needs at least one acceptance criterion, a known repo, valid factory config, a dod.md and no open dependency.
    • The readiness check flags item text that asks for credentials, CI changes or access outside the repo.
    • The scenario lock, red proof and @pbi scoping.
    • The review's BDD checks: every step definition asserts something, no scenario is pending or skipped, and no tag hides a scenario. They outrank anything in pr-review.md.
    • The path floors.
    • Agents never fill a human slot, and the approval count per tier.
    • A dod.md line left for the person who merges raises the PR to at least Medium, so a person is there to check it.
    • The factory's own DoD line: every scenario passes on main.
    • The self-review and address stages run the factory's own reviewer and addresser, whatever agent files the checkout holds. "One rubric" below gives the mechanism.
    My call
  • Coding standards. There is no policy file for them. Build agents already load the repo's own AGENTS.md or CLAUDE.md, so a team writes its conventions where its people already look. Because those files steer the agents too, they sit inside the path floor.
  • One rubric. The vendored self-reviewer and pr-reviewer keep only their review loop and report format. Their rubric comes from pr-review.md alone. The cell carries them under factory-only names, such as factory-self-reviewer. Claude Code prefers a repo's .claude/agents/ over the user's when two agents share a name (sub-agents), so a repo's own self-reviewer would otherwise replace the factory's. A checkout can still hold files under the factory-only names, because the repo is the factory itself or a branch added them. So a cell run that names one of the factory's agents passes the factory's own definition in the run's options. The Agent SDK ranks a definition passed that way above any .claude/agents/ file of the same name (Agent SDK subagents, "Filesystem-based definition"), so the self-review and address stages run the factory's reviewer and addresser whatever the checkout holds (PBI 96).
  • The PR reviewer only comments. Stage 8's reviewer is factory-pr-reviewer, passed in the run's options as the self-reviewer and addresser are, so a checkout's file of that name can't replace it. It reviews the one PR head its brief names against pr-review.md, says for each open thread in its brief whether that head settles it, and ends with APPROVED or OPEN: <n>. The repo host posts its findings as one review at that commit, with a body and line comments, and always with the COMMENT event. RepoHost.postReview takes no event at all, so the factory can't approve a PR or request changes on one, which keeps an agent out of every human slot. The repo host resolves a thread by its id, and resolving a resolved thread changes nothing (PBI 129).
  • Trust. Policy files are code, reviewed like code. Every change under .factory/, to AGENTS.md or CLAUDE.md, or under .claude/ needs a person. Agents follow them as the repo's instructions, while item text stays untrusted data.
  • Oversized items. The readiness judge also says whether an item is too big for one Sprint, as "oversized": true or false beside "flags" on its last line. A reply without it reads as false. Size alone never fails an item, since only the dor.md lines, the engine rules and the flags decide readiness. For an oversized item the factory asks the SOP's coding model, with no tools, for 2 to 4 child items. Each child has a title, a body naming the parent and the spec section or plan task it cites, the indices of the parent's criteria it takes, and the earlier children it needs. The split is valid only when every parent criterion goes to exactly one child and each child names only earlier children as needs. An invalid split posts no proposal, and the readiness comment, when there is one, says why a split couldn't be proposed (PBI 143). My call
  • Changing a policy. When any file the readiness check reads changes on the default branch, meaning a policy file or config.yml, the factory re-runs the readiness check on every NotReady item. So a team that loosens a rule or fixes a broken file doesn't have to touch each item. A run already started keeps the files from its pinned commit.
  • Visible results. Run detail lists every criterion with its result and reason. Floor's not-ready strip shows the dor.md lines an item failed. The PR body carries the dod.md checklist with the cell's results, a link to pr-review.md, and the review rounds.

07Concurrency

You wanted the number of items in flight to be configurable or worked out from past cadence. Yours The factory has three modes, set per factory:

ModeHow WIP is set
fixedA number in config, for example wip: 2.
adaptiveA formula, recomputed every hour over the last 14 days of history.
advisedThe formula sets the default, and a model proposes changes with written reasons. A proposal applies on its own only inside the formula's bounds. Outside them it waits for a human to approve it on the dashboard.

The adaptive formula

Little's Law says the average number of items in a stable system equals the arrival rate times the average time each spends inside, L = λW (Wikipedia). The factory's real limit is downstream, in how fast people review and accept its PRs. Starting more items than people can accept just grows the review queue, which breaks an anti-goal. So the rate in the formula is the human acceptance rate, and agent speed doesn't enter it.

demand = ceil(accept_rate × median_cycle_time) − max(0, review_queue − review_capacity) budget = floor(daily_budget ÷ median_cost_per_item × median_cycle_time) wip = min(clamp(demand, wip_min, wip_max), budget)

The clamp applies after the review-queue penalty, so wip_min stays the floor. The budget line applies last and can go below wip_min, down to 0, because money is a hard limit and WIP is not.

  • accept_rate. PBIs accepted per working day, last 14 days.
  • median_cycle_time. Working days an item holds a WIP slot, summed across its spells between InProgress and Accepted, same window. Time in Sign-off and Needs input is left out, because the item holds no slot there and Little's Law needs W to match what L counts. The budget line uses the same value.
  • review_queue. Factory PRs and scenario sign-offs waiting on a human right now. review_capacity is a config value, default 3.
  • Damping. WIP moves by at most 1 per hour. Lowering it only stops new starts and never kills a running cell. A WIP override from the dashboard applies at once and skips the damping.
  • Cold start. Until 10 items have been accepted, the factory runs fixed at wip_min.
  • Usage limits. On a subscription, the five-hour and weekly limits bind before dollars do. When an agent hits one, its cell checkpoints and stops, and the scheduler starts nothing new until the reset time the limit message gives. Flow shows limit stalls next to the WIP line. My call
  • Usage reserve. Those limits are shared with your own Claude use, so the factory stops early. When a usage-limit event reports utilization at or above usage_reserve_at, default 0.7, the scheduler starts nothing new until the reset time, and items already running finish. My call
  • Waiting on people. The review_capacity brake in §5 applies in every mode, on top of the formula. The formula's own penalty only shapes the number between those bounds.

Formula first. A model choosing the number on its own can't be audited or reproduced, and that number sets the spend. The formula fits on one dashboard panel. The model still earns its place in advised mode, for things the formula can't see, like a holiday week or a release freeze noted in the backlog. My call

09Safety

  • Untrusted item text. Anyone who can edit a backlog item can plant instructions in it. Agents read item text as requirements to weigh and never as commands. The readiness gate flags items that ask for credentials, CI changes or access outside the repo. On a public repo anyone can also review a factory PR, so a review, and each review comment, steers the factory only when its author maps to an allowlisted user. Anyone else's review requeues nothing. The agent that addresses reviews is handed only trusted authors' comments, checked one by one, because a stranger can reply inside a thread an allowlisted user opened.
  • Least privilege. One bot identity per backlog system, with access granted repo by repo and never org-wide. Phase 0 makes one exception, because it dogfoods on a personal account. GitHub documents Project access by GitHub Apps only for organizations, so the factory reaches a personal board with the owner's own gh CLI OAuth token, the owner's decision on 2026-11-06. That token can't be narrowed to the board: gh always asks for at least repo, read:org and gist, and the owner's token also holds admin:org, workflow and user. So in Phase 0 the control plane holds write on every repository the owner can reach, the owner's admin bypass of branch protection, and the power to edit CI workflows. Only the control plane holds it, and cells never see it. It has no expiry, and neither a new gh login nor gh auth logout revokes it, so the control plane's copy outlives both. Revoking it means revoking the GitHub CLI's access in GitHub's settings, which signs out every gh session. A project-only classic token was the narrower option the owner declined. Board edits show as the account owner. The App still does every repo action. Each cell gets a short-lived token for one repo and no production secrets, and never the owner's Claude token. A cell holds a stand-in for its own run and sends model calls to the control plane's model gateway, which checks the stand-in and swaps in the owner's token, so nothing a steered agent writes can carry it. The control plane mints the cell's GitHub token with an explicit permissions set: write on contents, pull_requests and issues, for item comments, and nothing on statuses or checks. Without that set the token gets "all of the permissions that were granted to the app" (GitHub), and a cell steered by planted item text could post a green risk-approval on its own PR. Only the control plane posts that check.
  • Platform-enforced protection. Branch protection and required reviews live in the git host's settings. A confused agent can't talk its way past them because no prompt controls them. The one check the factory posts itself, risk-approval, is pinned to the factory's App, and that App holds no admin or bypass rights (§6). A compromised control plane could still post a false green on that check. That residual risk is why the App's private key sits in Key Vault, where only the control plane's managed identity can read it. Phase 0's repo is public, which is what lets GitHub's Free plan give it branch protection and deployment environments with required reviewers (GitHub). main takes changes only through a PR with one approving review and a green lint check, so a cell's write on contents can't reach it. The owner, as admin, bypasses those rules, so they can merge their own PRs. The Azure deploy runs in a production environment whose required reviewer is the owner.
  • Network. An egress allowlist limits cells to the factory's control plane, the git host, the backlog API and package registries. Cells reach the model API only through the control plane's model gateway. Anthropic's servers can reach the web for a model request, through server-side tools or a URL in an image or document. So the gateway refuses both, except web search, which a repo turns on only by listing it in web_tools (§6). It checks the request it parsed and forwards that copy, so nothing it didn't read reaches the model. Locally the allowlist is an HTTP proxy on an internal Docker network, because the sandbox can't start there (§11).
  • Budget caps. Per item, per day and per month. The daily cap pauses new starts. The item cap sends the item to Needs input. So does the SOP's wall clock, which counts only time the item holds a WIP slot, so waits in Sign-off and Needs input don't use it up.
  • Kill switch. One dashboard button and one config flag. Either stops every cell within a minute.

10Failure and recovery

  • Checkpoints. The branch is the checkpoint. Each stage commits its output and the state store records the last stage completed. A new cell picks up from there.
  • Stale branches. At every claim, before the next stage runs, the cell merges the base branch into the item's branch, because other items may have merged while this one waited. A conflict the agent can't resolve goes to Needs input.
  • Idempotent steps. Opening a PR, commenting and setting status each check current state before acting, so a retry never creates duplicates.
  • Retry budget. Set per stage in the SOP, plus a total per item. When it runs out, the item moves to Failed with a summary of every attempt.
  • Quarantine. Three failures in a row on one repo pause that repo and raise a dashboard alert. A streak like that usually means a broken build or a bad SOP change, and the items themselves are fine.
  • Control plane restart. Leases and the event log live in Postgres, so a restart loses nothing. Cells keep running, and the scheduler finds them again through their lease renewals.
  • Lost database connection. When Postgres ends a connection, because an administrator ended it, the server restarted or the network dropped it, the control plane logs it and keeps running. That holds for a connection lost while a transaction or the webhook holds it, as well as for an idle one: the work in flight fails and is logged, and the dead connection is dropped. The pool opens a fresh connection for the next query, so the next scheduler tick and board poll succeed once Postgres is back, and one that runs while it is down fails, is logged and is retried on the next run. The dashboard's live event stream ends its open streams, so each browser reconnects and listens again on a fresh connection.
  • Stuck transaction. A database transaction that never ends, such as one holding a lock it never releases, can stall the scheduler, the board poller or a cell's request to the cell API without an error, so nothing fails and nothing would be logged. Long-running work speaks up instead. A scheduler tick or a board poll still running after 5 minutes logs how long it has run and the step it is in, and logs again every 5 minutes until it ends. A cell API request still open after 60 seconds logs its route and run id. The warning only reports the stall. It doesn't cancel the work, so a person reading the log finds the stuck step and ends the transaction behind it. The factory logs rather than leaning on a database timeout, because statement_timeout and idle_in_transaction_session_timeout act through the backend's interrupt check, which a backend stuck this way never reached, so neither would have ended the stall.

Caps to start with. $40 per item, $75 per day and $1,000 per month, all counted at API rates from each run's token usage. My call On a subscription these protect your shared usage limit, not your card. Usage credits stay off, so the monthly bill is the plan fee plus Azure, about $300.

Model billing

Subscription billing. Models run on your Claude subscription. Yours You chose it with these terms on record, quoted as fetched on 2026-11-05:

  • Consumer Terms §3. "You may not access or use, or help another person to access or use, our Services in the following ways: ... Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." (Consumer Terms, effective Oct 8, 2025)
  • Consumer Terms §2. "You may not share your Account login information, Anthropic API key, or Account credentials with anyone else. You also may not make your Account available to anyone else."
  • Agent SDK docs. "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead." (overview)
  • Pointing the other way. "For CI pipelines, scripts, or other environments where interactive browser login isn't available, generate a one-year OAuth token with claude setup-token", which "requires a Pro, Max, Ultra, Team, or Enterprise plan." (authentication)

How the factory runs on it:

  • Token. You run claude setup-token once. The token goes into Key Vault and stays with the control plane. Cells reach the model through its gateway, which Claude Code supports through ANTHROPIC_BASE_URL (Claude Code), with a stand-in token for the run in CLAUDE_CODE_OAUTH_TOKEN. Your token lasts one year and is tied to your subscription, so the dashboard warns 30 days before it expires.
  • No bare mode. Bare mode "does not read CLAUDE_CODE_OAUTH_TOKEN" (GitHub Actions doc), so cells never run with --bare.
  • Test first. The Agent SDK docs don't say whether the SDK honours the OAuth token. Phase 0a checks it first, in a local cell container, and Phase 0b checks it again in Azure. If the SDK refuses it, cells drive the claude CLI headless instead, which documents the token.
  • Shared limits. The five-hour and weekly limits are "shared across Claude and Claude Code" (help center), so the factory and your own Claude use draw on the same allowance. §7 covers how the scheduler reacts when a limit hits.
