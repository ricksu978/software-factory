Software Factory

A cloud service that never stops. It watches one or more Scrum backlogs, takes Product Backlog Items one at a time or several in parallel, and runs each through a written SOP with Claude agents. Every item that meets the Definition of Done ships as an Increment.

Yours you asked for it My call a default you can override All decisions logged in §14

01Intent

Refined, ordered backlog items sit waiting for a developer to free up. The factory takes the routine ones, so people spend their time refining the backlog and reviewing and accepting work.

Throughput and quality are measured together. The factory is working when its Increments pass the same Definition of Done as human work, cost per item is one the team accepts, and people spend less time per item than they would building it themselves.

02Scope

Goals

  • Runs in the cloud 24/7. Yours
  • A private dashboard for reporting and monitoring. Yours
  • Watches backlogs, picks PBIs, runs the SOP, delivers an Increment. Yours
  • Concurrency is a fixed number or comes from past cadence. Yours
  • Any orchestration decision can be overridden from the dashboard. Yours
  • BDD and TDD by default. Behaviour is written in Gherkin at planning, and every test fails before the code that makes it pass. Yours
  • PRs are tiered Low, Medium or High risk and need 0, 1 or 2 human approvals, the model Anthropic's Claude Code team uses. Yours
  • Every run is auditable, down to the SOP version, model and cost. My call

Non-goals

  • Writing or ordering the backlog. The Product Owner keeps that. My call
  • Running Sprint events. The factory feeds Sprint Review and nothing more. My call
  • Production deploys in v1. The factory stops where your Definition of Done stops, staging at most. My call

Anti-goals

The factory has failed, even if it runs, when it:

  • merges work a human reviewer would have rejected,
  • touches items or repos nobody gave it,
  • adds to human review load,
  • spends money it can't account for item by item.

03Scrum terms the factory uses

The factory follows the 2020 Scrum Guide. Two passages set its delivery rule.

"The moment a Product Backlog item meets the Definition of Done, an Increment is born." Scrum Guide 2020, Commitment: Definition of Done, scrumguides.org
"Multiple Increments may be created within a Sprint. ... However, an Increment may be delivered to stakeholders prior to the end of the Sprint." Scrum Guide 2020, Increment

So the factory never holds work for the end of a Sprint. Each PBI that passes the DoD gate becomes an Increment right then. At Sprint Review, the team presents the sum of that Sprint's Increments.

Ready The Scrum Guide has no formal "Ready". It says only that items which can be Done within one Sprint are "deemed ready for selection". So each repo writes its own Definition of Ready in .factory/dor.md, and the factory checks every item against it. The engine itself checks only the rules listed under "What stays in the engine" in §6, plus the opt-in label. An item that fails gets a comment listing the lines it failed and stays in the backlog. Component Job Notes
Backlog watcher Mirrors eligible items from each backlog into the state store. Takes webhooks where the backlog system sends them, and polls every 5 minutes to catch missed events. Each backlog system gets its own adapter, described below. My call
Readiness gate Decides whether an item can enter. The engine's own checks run first. Then a cheap model judges the item against the repo's dor.md, line by line. It comments on items and edits none, except a parent whose split it files, which loses its opt-in label, and a child it filed that fails dor.md lines, whose body it rewrites once (PBI 264, §6). For an item the judge reports too big for one Sprint, the gate also asks the SOP's coding model to propose a split, once per item text, and files a valid one as child items (§6, "Policy files"). My call
Scheduler Starts a cell when a WIP slot frees up. Follows backlog order. Takes the top ready item and skips any whose dependencies aren't Done. See §7.
Work cell Runs one PBI through the SOP in an isolated sandbox. Fresh clone, its own branch, a token for one repo, a budget cap. Saves a checkpoint after every stage so a crashed cell can resume.
State store The one source of truth for items, runs, stages, costs and WIP policy. Postgres. Every state change is also appended to an event log, which feeds the dashboard and the audit trail. My call
Dashboard Reporting, monitoring and a few controls. See §8.

  • Claiming. The scheduler takes a lease on the item and the cell renews it every 60 seconds. After 5 missed renewals the lease expires and the item goes back to Queued, branch intact. Every attempt of the item's run still marked started is then closed as stopped, ending at that moment, with a message saying the cell's lease ran out, so a dead cell's attempt never stays open. A restart or a drain that ends a cell's claim at a stage or attempt boundary, and so sends its item back to Queued, closes them the same way (PBI 301, PBI 379). Like any stopped attempt, such an attempt uses up none of the stage's retries (PBI 239). After a failed attempt with retries left, the item waits in Queued at the same stage, and the next claim spends only the retries left (PBI 393). Each lease carries a generation number that goes up on every claim, and again whenever the item leaves InProgress. A cell checks its generation before every push, comment and state write, and exits once it no longer holds the lease. It also stops itself after 3 minutes of failed renewals, before the 5-minute expiry, so an old cell is gone before a new one starts. My call
  • Needs input. The agent posts its question as a comment on the item and in the dashboard. You answer in either place. On the item, a comment that starts with /answer counts, and only when its GitHub login maps to a user on the dashboard's allowlist, so ordinary discussion on the item is never taken as an answer. The item gives up its WIP slot while it waits, so one stuck item can't stall the line. The factory reminds on the item and on Floor at day 2 and day 4, and after 5 days with no answer the item is Abandoned. My call
  • Sign-off. Scenarios wait for the Product Owner the same way. On the item, a product owner comments /approve, or /changes followed by a note. The sign-off view lists each acceptance criterion beside the scenarios tagged with it and flags any criterion with none. Above the buttons it also shows a Scope section with the issue's body as written on GitHub, and every feature file up for sign-off in full, as it stands at the scenarios sha, so the owner can judge the scenarios against the work without opening GitHub. An empty body shows no Scope section. A timed-out item that can still be signed off shows the same view. Reminders and the 5-day limit work as for Needs input.
  • Waiting on people. An item that waits for a person holds no slot, so the WIP number alone doesn't bound the work landing on people. In every concurrency mode the scheduler starts no new item while the items waiting on a person reach review_capacity, default 3. Those are items whose question or sign-off is still unanswered, items in FeatureChangeRequest (PBI 366), plus factory PRs waiting on a reviewer. An item whose answer has arrived can always resume, so answering never stalls the line. A priority-1 item, its own priority or one it inherits, gets past this brake too, so what matters most is never kept waiting by it, as #305 and #317 were on 2026-11-15 (PBI 320). Floor shows the count beside the WIP number. My call
  • Claim order. Every item has a priority from 1 to 5, where 1 is the highest, read from the board's Priority field on each poll. A missing value, or one that isn't a whole number from 1 to 5, counts as 3. An item is final-stage while its PR is open and it's in the review loop: InReview, at address, or at the PR review that follows address. Every final-stage item is in one group, whichever of those stages it's in. The scheduler claims Start now first, then the final-stage group, then every other item, and within each group by priority, 1 first. Within one priority the order is as before: answered items first, then the factory queue's order, which Move up and Move down change. An item that carries the board's bug label, read on each poll beside the priority, comes before the rest within its priority in the final-stage group, and before the rest at priority 1 outside it, ahead of answered items; at priorities 2 to 5 outside the group the label doesn't change the order. Only the item's own label counts: an item that takes its priority or group from a bug item doesn't take its label, and Floor and Run detail mark only the item that carries it (PBI 378). An item that a final-stage item depends on, directly or through other items, joins the final-stage group with that item's priority, wherever it is in the pipeline, so it's picked up to unblock its dependent. Outside the group, an item that a higher-priority item depends on takes that priority. Either way the item goes back to its own group and priority once the dependency is gone, or once the item depending on it is Done or otherwise finished. Floor and Run detail show each item's priority and whether it's final-stage, and name the item either one comes from when it isn't the item's own. The priority isn't judged and doesn't re-gate an item, unless the repo lists Priority as a readiness field: then dor.md can refer to it like any other readiness field, and setting or changing it sends the item back through the readiness check. A priority-1 item still never gets past a hold, an open blocker or the readiness gate (PBI 320). My call
  • Coming back. A Failed or Abandoned item returns to Queued when an operator re-queues it, and an Abandoned item also returns when its question gets a late answer. An item that failed its Definition of Done on main also returns to Accepted on its own when a re-check finds the merge no longer broke main, as Red main in §10 describes (PBI 369). An item withdrawn from Eligible or NotReady never passed the readiness gate, so a re-queue sends it back to Eligible to meet the gate instead (PBI 168). It resumes at its last checkpoint, except when its PR has already merged; then it starts a new run on a new branch. When a person closed its PR without merging, it resumes at Open PR, which opens a fresh PR from the same branch. A merge or a close that happens while the item is In progress, during address for example, or while it waits in Needs input after its PR opened, counts the same way: the webhook, or the poller when no webhook came, moves the item to Accepted or withdraws it. A move to Accepted from Needs input closes the open question, so the dashboard stops asking for an answer, and a Needs input item whose PR is still open keeps waiting (PBI 194) unless the factory merges it under stage 10's rules (PBI 262). An address run that found no trusted review text and no conflict used to ask "no trusted review text to address", before PBI 258 made it pass instead, and an item may still wait on that question. Once the poller reads that item's PR as conflicting with its base, or a trusted review or a comment in a still-open thread newer than the question asks for changes, the factory answers the question itself, naming the conflict or the review and its time and naming nobody as the one who answered, and logs the re-queue as a system event. The item is then claimed again at address. A person's answer, a Hold or an earlier poll that got there first wins, a held item is re-queued only once it's released, and an item waiting on any other question still waits for a person (PBI 305). An item that asked the older "Address failed" question before a CI failure went back to Green (PBI 292), that is before PR #309 merged at 2026-11-15T05:50:19Z, is answered the same way once every finding the question names is a CI failure: the answer says the factory sends the item back to Green to fix the CI failure, names nobody as the one who answered, and the re-queue is a system event. The item is then claimed again at Green. The claim merges the base, as every claim does, and Green's findings are the failed checks of the PR's head as it is now, each with its URL and failing tests. A question that names anything besides CI failures still waits for a person, and a person's answer, a Hold or an earlier poll that got there first wins. So does the same question asked since then, which is address giving up after CI failed on each of its own fixes: that run stopped before it posted its thread replies, so only a person's answer, which reruns address, gets them posted, and a re-queue to Green would skip address and leave the reviewer's threads unanswered (PBI 317). A cell that reaches Open PR, or starts an address run, on a branch whose PR has already merged opens nothing, calls no agent and ends the stage as failed, naming the merged PR. Address asks before it merges the base, so a squash-merged branch never conflicts its way into a question. A stage that waits for CI on its push, Open PR, address or PR review, may find the factory refusing to say whether CI passed, because a person merged the PR meanwhile and the commit is gone from the branch or now on main. The stage then asks for the PR's state. A merged PR ends it the same way, naming the merged PR, and one closed without a merge ends it naming the closed PR, for the poller to withdraw the item. Neither asks anyone, runs another attempt or moves the item. A refusal while the PR is still open fails the attempt as before, so a cell can't learn CI on a commit that isn't its own (PBI 212). An item re-queued while its question is still open goes back to waiting, with a fresh 5-day clock, unless a person closed its PR without merging: then the question closes and the item resumes at Open PR, so the next poll doesn't withdraw it again over the same closed PR (PBI 194).
  • Backlog changes. The watcher compares each item in the factory with the version the run started from. When the acceptance criteria change, the factory comments on the item, closes its PR if one is open, and starts a new run from Understand on a new branch from the base, which leads to a new sign-off. A fresh branch matters because the old one already holds code, so new scenarios would pass before Red. When the opt-in label is removed or the item is closed, the factory stops the run, frees the slot, closes the factory's PR with a comment, keeps the branch and moves the item to Abandoned. An Eligible or NotReady item that loses its label or closes is withdrawn to Abandoned the same way, on the next poll and before the readiness gate sees it, so it leaves Floor's Not ready items under "Waiting on you". It has no run, so there's nothing to stop or close. If such an item gets its label back, it returns to Eligible on the next poll and meets the readiness gate again, so it never reaches Queued without passing it. An item withdrawn from Queued or later stays Abandoned when its label comes back (PBI 168). A Split parent stays Split when it loses its label, gets it back or closes, since its work goes on in its children (PBI 225). Its one way out is to Done, once every child the factory filed for it is Done (PBI 226). A parent split before PBI 225 lost its label once its split was filed and was withdrawn to Abandoned. Each poll first moves such a parent to Split, once, before it could return to Eligible: an Abandoned item withdrawn from Eligible or NotReady with a split kept for it, and every child of that split among its sub-issues by its split marker. It then reaches Done like any Split parent. An Abandoned item with no kept split, or one abandoned any other way, stays Abandoned (PBI 228). An item waiting in FeatureChangeRequest takes the same backlog changes as one in InProgress: a label removed, the item closed or its PR closed unmerged withdraws it to Abandoned, a change to its acceptance criteria queues it again for a new run, and a rules section that no longer reads as approved sends it back to Eligible. A person who merges its PR while it waits moves it to Accepted, which the poller and the merge webhook both notice (PBI 364). All of these moves are logged as system events. My call
  • Board status. The factory owns the status field of the items it holds. The project's built-in workflows that set status, such as item closed and pull request merged, stay off. A factory PR references its item with Refs #n, so a merge doesn't close it, and the factory closes the item when it reaches Done. Yours
  • Assignment. While an item is in the factory, it's assigned to the factory's bot account, so no person picks it up at the same time. Where the git host can't assign the bot, a factory:in-progress label does the same job.
  • Overrides. A dashboard override can move an item along paths the diagram doesn't draw, such as holding a queued item or sending a reviewed one back to Specify. Each such move is logged as an override event. See §8.

06SOP

You said the SOP is still to be defined. The factory treats it as data, a versioned file in a repo. Each run pins the SOP version of the cell image on its first claim. A cell image holds only one SOP, so when a run pinned to an older version resumes, it moves to the image's SOP and carries on from the stage it was at. The run records the new version, and the factory logs the move as a system event on the item. The one run that can't move is one whose next stage the image's SOP lacks. That run asks for input, and the question names the stage. Below is a v0 to start from. It works outside in. Gherkin scenarios define the behaviour at planning and must fail first. Unit tests then drive the code inside each scenario, and the scenarios pass last. Review uses the agents you already run.

The factory drops the agent's chatter first: a summary wrapped in a fenced block keeps only the fence's contents, and text before its first ## heading is left out. A wrapper that opens with a markdown or md info string, or none, closes at the first fence-only line that leaves no code block inside it open, so code blocks inside it are kept (PBI 291) and a note after it, with its own code block, is left out (PBI 297). When a fence-only line could close the wrapper or open a bare code block inside it, and a ## heading after it only counts if it opens one, the line opens a bare code block if a later fence-only line then closes the wrapper with no code block inside it open, so a wrapped body with a bare code block before more sections reaches the PR whole (PBI 291). A line spaced as a closing fence, with text right before it and a blank line after it, gives the finding below instead, since a bare code block that starts with a blank line is spaced the same as a wrapper's end before a note whose code block holds a ## line, and closing the wrapper there could silently drop the sections after that block (PBI 297). With no such heading, the line's spacing decides: text right before it and a blank line after it closes the wrapper, and a blank line before it and text right after it, with its block's closing fence spaced as one, opens a bare code block, so a bare code block with text after it in the body's last section is kept whole too (PBI 291). When no such line closes the wrapper, or the spacing fits both readings, the factory can't tell where the body ends, so the attempt fails with a finding that says so, and the retry asks for the body alone (PBI 297). A body that leaves a code block open fails the attempt, and the retry asks for the body alone (PBI 291). A summary that still doesn't start with ## Problem fails the attempt, and the retry asks for the body alone (PBI 216). The body lists each scenario with its red and green result and states the review rounds. CI green. A check run that was cancelled neither failed nor passed, as when GitHub cancels a push's run because a newer push to the same branch started under concurrency: cancel-in-progress. No read of a PR's or a branch's checks takes it as failed or as passed (PBI 423). A commit whose only unpassed checks were cancelled isn't green: the cell API answers cancelled for it, names no failed check, and gives each cancelled check the conclusion cancelled. A check that failed beside a cancelled one is still a failure, and it is the only one named. A timed-out check and one that needs action still count as failed. Before a red CI is charged to the attempt, the factory re-runs the failed checks once, and only those, so a flaky check doesn't cost an attempt. A check run that was cancelled is neither failed nor passed, and it is never charged. When a later push to the branch cancelled the run a stage waits on, the stage ends its wait without charging the attempt, and the item goes back to Queued at the same stage, so its next claim starts from the branch's newest commit. A later push cancelled the run when CI on the commit a stage pushed reads cancelled and the run's branch on origin has moved on from that commit. The stage ends its wait at once, whatever the pending CI cap, and reports its attempt stopped, so it goes to no Green pass. The item goes back to Queued through the event ci_superseded, and its next claim clones the branch, reads CI there, and starts the stage afresh rather than resuming the stopped attempt. An operator's stop-run on the item still wins: the claim stays, and the item is failed and held as any stopped run is. When the branch still points at the commit, as when a person cancelled the run, the cell waits as it does for pending CI, for a re-run or a push, and after 60 minutes asks a person instead. A pass on the re-run counts as green, and the stage's message says which check was re-run on which commit and that it passed. A check that fails again is charged as before, and only the checks that failed on the re-run go back, each with its re-run's URL. When the repo host won't start the re-run, the failure is charged as it stands, and the message says the check couldn't be re-run (PBI 233). When it re-runs some of the checks and refuses others, the refused ones are charged as they stand with that note, and the factory waits only on the ones it re-ran. The factory reads which checks failed only once no check on the commit is still running, so a check that fails later is re-run too. It waits until each re-run check shows a new run, either at a new URL or finished later than its old run, and that run has finished, before it reads CI again. A note for a check whose re-run still reads as running says its re-run hadn't finished. The control plane records each re-run by run and commit and refuses a second one, so a run resumed after a restart can't re-run the same commit's checks twice. CI failures go back to stage 5. Green's findings name each failed check, its URL and the tests it names as failing, read from the failed GitHub Actions job's log, and a check whose log names no test, or one the factory can't read, is named with its URL alone. Green's findings also carry the last 100 lines of each failed check's log, which the cell API reads from the repo host, so the cell needs no GitHub access to learn why CI failed. A new commit on the branch clears it, whether Green's fix, a person's push while the item waited or the claim's merge of a newer base, and CI is read on that commit as usual (PBI 315). When Green leaves that commit unchanged, CI has nothing new to judge, and the item goes to Needs input instead of Failed. Green running out of retries still fails the item. The question names each failed check with its URL and failing tests, each commit CI failed on, and how many times Green tried. Before it goes back to Green, the cell reads CI on the base commit, origin/<base>. A summary that doesn't start with ## Problem, or an agent call that fails, gets 1 retry, then goes to Needs input (PBI 216). CI still pending 60 minutes after the cell began waiting on a commit goes to Needs input, with a question naming each check still pending. BDD rules

  • Traceability. Every acceptance criterion gets a tag, and at least one scenario carries it. Stage 2 fails on any criterion without a scenario. Each feature file also carries its PBI's tag, such as @pbi-482. Red and the traceability check look only at that PBI's scenarios, and the lock covers only its files. Green runs the whole suite, so earlier Increments' scenarios keep guarding against regressions.
  • Business language. Scenarios describe behaviour the Product Owner can read, with no selectors, SQL or class names. Implementation detail belongs in step definitions. This rule, and a Rule per business rule with scenarios for the happy path, edge cases and failures, make up the default scenarios.md. A repo can replace them. The other rules in this list belong to the engine.
  • The lock. At sign-off the factory records the commit of the feature files. After that the build may add step definitions and unit tests, but it may not edit, skip or tag out a locked scenario. Every later gate compares the feature files against the lock. Every agent that works after sign-off is told which feature files are locked. When a stage's work changes one anyway, the factory restores the locked files to the lock commit, commits that, names the restore in the attempt's findings and carries on, so the next attempt or round starts from the signed-off scenarios. At red, green and address the attempt fails and retries. Self-review and open-pr carry on with the restored files. The owner is never asked about it, since no answer would change the files. A stage that thinks a locked scenario is wrong may ask to change it instead (PBI 364). Its agent edits the file as it would have it, and its report names each such file and the reason, one line each, FEATURE CHANGE: <path>: <reason>. The factory still restores the locked files to the lock commit, pushes the rest of the stage's work, and moves the item from InProgress to FeatureChangeRequest, where its run goes no further. The request holds each file's text at the lock commit and the version the stage proposed. The item page shows it under "Feature change request": each file's path, the stage's reason, and its lines before and after. The PBI gets it as one comment, the way sign-off posts the scenarios, with each file's change from the lock commit as a diff. The Product Owner answers the request with the /approve or /changes <note> used at sign-off, or with Approve the change or Ask for changes on the item page (PBI 365). Only the Product Owner decides, as at sign-off (§8). /approve commits the proposed files to the item's branch in one commit on top of the stage's work, and moves the lock to that commit, so every later gate compares the feature files against the new lock. /changes keeps the lock where it was, and the stage that asked gets the note in its findings. Either way the item goes back to Queued, and the run resumes at the stage that asked. While it waits, the item waits on a person as one in SignOff does, with one difference: it is never abandoned for waiting (PBI 366). It holds no WIP slot, and it counts toward review_capacity (§5). The factory comments a reminder on the PBI 2 days and 4 days after the item moved to FeatureChangeRequest, once each, and no reminder says the item will be abandoned. It stays in FeatureChangeRequest until the owner decides, or until a person merges or closes its PR, removes its label, closes the item, changes its acceptance criteria or edits its rules section (§5). Floor's "Waiting on you" and the state line of the item's Run detail show it as waiting on the Product Owner, with a "Feature change request" link to that section of Run detail, on the dashboard and in the SPA. Pr-review runs while the run stays at open-pr or address, so a request its addresser raised resumes the run there, and the note waits for the next pr-review, whose addresser gets it in its brief. An address with no trusted review comment runs no agent, so its attempt says the findings it carried went unread. A request that names a file the stage didn't change, or one that isn't locked, asks for nothing. The self-reviewer holds no finding open for a scenario change. A scenario it thinks is wrong goes in the PR body as a note for the person who merges. The run keeps those notes, so a PR body written in a later claim, after a usage limit, a stop, an answered block or a requeue, still carries them. A scenario that turns out wrong goes back to Specify and through sign-off again. My call
  • Red proof. A scenario that passes before any behaviour exists tests nothing new, or its steps don't assert. Stage 4 reports it as a finding and doesn't proceed. A scenario tagged @regression is the exception. It restates behaviour that already holds, such as "every existing test still passes", so Red needs it green instead, and a red or crashed one is the finding. An item whose every scenario is @regression fails Red, because Red then proves nothing. Red expects only the scenarios the repo's bdd.run selects with its own tag filter, such as --tags "not @local". The factory learns which those are by running bdd.run with --dry-run added, since cucumber-js reports a test case only for a scenario its filter selects, wherever the filter is set: in the command, in a profile, in an environment variable, or in an npm script the command runs with a trailing --. The added flag has to reach cucumber-js: npm run <script> keeps a trailing --dry-run for npm unless the command already passes --, and a trailing || true or pipe sends it elsewhere. So Red checks that the report really comes from a dry run, with no step that ran, and fails with a finding that says so when it doesn't, rather than read a real run, which leaves out a selected scenario that didn't run, as the list of what bdd.run selects. A scenario bdd.run leaves out runs on the owner's machine instead. So a scenario that filter leaves out doesn't count against Red, while one it selects that doesn't run fails Red as not run in the cell. An item none of whose scenarios bdd.run selects fails Red, since nothing then proves it red. Traceability still counts every scenario, filtered or not. Green treats @regression like any other scenario.
  • Runners. Each repo uses its existing Gherkin runner. Cucumber lists official implementations for JavaScript, Java, Kotlin, Ruby, Scala and C++ (cucumber.io). For .NET, Reqnroll is "a Cucumber-style BDD test automation framework" built as "a reboot of the SpecFlow project" (reqnroll.net). A repo with no runner gets one in its first factory PBI, and its commands go in the repo config. My call
  • Proving a scenario steady. A scenario that fails now and then turns main red and fails items that had nothing to do with it. npm run bdd:repeat -- --times <n> --name "<scenario name>" runs the one scenario with exactly that name n times, one run after another, each in a cucumber-js process of its own, as npm run bdd runs it. A failed run doesn't stop the runs after it. The script names each failed run with its output, says how many of the n passed, and exits 0 only when every run passed. Each run ends as soon as cucumber-js has reported, so a handle left open doesn't add to its time. A name that matches no scenario fails, and so does a run count that isn't a whole number above zero, which runs nothing. A fix for a flaky scenario shows 20 passing runs in a row, and a scenario that waits for something keeps the same deadline, so it still fails when the behaviour doesn't happen (PBI 376). My call
  • Moving time on instead of waiting it out. The worker sets every timer it uses, and reads every time it records, through one clock it's given (PBI 396): the scheduler tick, the outbox loop, each board poll, the standby's lock retry, the holder's lock check, and the slow-work warnings of a tick or a poll. Without one it runs on the real clock, at the intervals it always has. A scenario hands it a fake clock, which stands still until the test moves it on. Moving it on fires each timer that falls due, one at a time and at its own time, and waits for the work each one starts before it fires the next. A closed lock connection still reaches the worker as an event, so a worker whose fake clock never moves still exits when it loses the lock. A worker that stops gives the lock back before it closes its lock connection, so a standby's next try on its fake clock finds the lock free. So PBI 157's and PBI 158's scenarios move their workers' clocks on where they used to sit through real lock retries and ticks, and a takeover scenario no longer waits 15 real seconds. A Then that gives the workers some seconds still counts real ones, so it fails when the behaviour doesn't happen. My call
  • Running the suite in parallel. npm run bdd runs the scenarios in cucumber-js's own parallel workers (PBI 390), so a cell's Red and Green and every CI build finish the suite in a fraction of the time. How many comes from one setting, BDD_WORKERS, so a cell, CI and a person's machine can each set their own. Unset, it is 4. A count that isn't a whole number above zero is refused before anything runs. A scenario that can't share the machine with another carries @serial, on itself or its feature. The suite's parallel rule starts it only when no other scenario runs, and starts no other while it runs. The @local scenarios that drive the AppHost, Docker or the owner's accounts carry it. No step starts a server on, or connects to, a port fixed in its code: a step that starts a server takes a free port, picked below the range the OS takes outgoing connections' ports from, and each port a scenario names stands for a free port of that scenario's own. A check over the step definitions names any step that breaks this rule, by file and line. Every worker writes into the one Cucumber Messages report, so Red and Green read each scenario and its result as they did from a serial run. My call
  • Reading runner results. Every runner writes a Cucumber Messages report, the format the Cucumber project calls "the preferred standard" (cucumber/messages). Reqnroll writes it from v3.0 (Reqnroll formatters). The factory reads step statuses from that report and never parses console output. A scenario counts as red only when its first non-passing step is FAILED and is an Outcome step, a Then. Any UNDEFINED, PENDING or AMBIGUOUS step, a failed hook, or a failure in a Given or When counts as a crash. A missing or empty report gives no verdicts, so Red fails every expected scenario as not run, and Green fails too (schema). cucumber-js writes testRunStarted first and testRunFinished last, so a report with the first and not the second is one whose run didn't finish, as when the cell stops bdd.run at its time limit. Red and Green then fail on one finding that says the BDD run didn't finish and names each scenario that was running, on any of the run's workers, and report none of its unfinished scenarios as failing or crashed (PBI 399). My call

Risk tiers

Stage 9 copies the approval model from "How the Claude Code team does code review" (claude.dev, 2026-10-15). The table is theirs, word for word. Yours The approvals column is the engine's. The examples column is the default risk.md, and a repo replaces it with its own examples of what each tier means there.

Risk Examples Human approvals
Low Docs, copy, internal-only features, additive changes behind a flag None required once automated review and security checks are green
Medium Ordinary product changes, and changes to sensitive areas such as caching, the auto-updater, or system prompts One person
High The highest-risk code, plus a small set of paths that always need two people Two people
  • The change sets the tier. A classifier reads the diff and the repo's risk.md, and picks the tier, whoever or whatever wrote it. A second pass asks whether this particular change needs a person even when its tier says no. Path rules run first, and no risk.md can lower them. CI workflow files, the repo's sensitive_paths, anything under .factory/ or .claude/, and AGENTS.md or CLAUDE.md anywhere in the repo always need at least one person. Those files steer the factory's own agents, so a change to them must never pass at Low. The classifier uses the coding model, because a wrong Low lets code skip review. My call for the model.
  • Agents never fill a human slot. Approvals from self-reviewer, pr-reviewer or any other agent don't count toward the number. A Low PR merges without a person only once automated review and the repo's security checks are green.
  • Trusted authors. In the source, only authors on a repo's trusted list get the lighter paths, and everyone else needs a second person. The factory's bot account is treated as an author like any other. It gets the table's numbers only in repos whose owners add it to the trusted list. Elsewhere a factory PR needs one more person than its tier says, up to two. Yours for per-repo trust, My call on how to read "a second person".
  • No directing person. In the source, whoever prompted an agent counts as one of its reviewers. A factory item has no such person, so every required approval comes from a reviewer.
  • One commit per approval. An approval covers the commit it was given on. When the factory pushes after an approval, for example pr-addresser fixing a thread or resolving a conflict, the approval no longer counts and the factory asks again. One exception keeps stage 8's base syncs from adding review load. An approval still counts when every commit since it is a merge of the base that leaves the PR's diff unchanged. The factory checks that by comparing the patch-id of git diff base...head at the approved commit and at the new head.
  • Enforcement. Low needs zero approvals, so the git host can't require a fixed review count. The factory posts a required status check, risk-approval, that turns green only when the tier's approvals are met on the head commit. Branch protection requires that check with the factory's GitHub App as its expected source. GitHub then blocks the merge "if the status is set by any other person or integration" (GitHub). The App has no admin rights and is on no bypass list, so it can't change the protection that checks it.
  • Review requests. Once the PR review stage passes, the factory requests reviewers from the repo's CODEOWNERS file, or from reviewers in .factory/config.yml when the repo has no CODEOWNERS. Floor shows how long each PR has waited. My call
  • Visible tier. The PR body and the dashboard show the tier and the classifier's reasons, so a reviewer can challenge them. An operator can raise a tier. Nothing lowers one, overrides included.

The adaptive formula

Little's Law says the average number of items in a stable system equals the arrival rate times the average time each spends inside, L = λW (Wikipedia). The factory's real limit is downstream, in how fast people review and accept its PRs. Starting more items than people can accept just grows the review queue, which breaks an anti-goal. So the rate in the formula is the human acceptance rate, and agent speed doesn't enter it.

demand = ceil(accept_rate × median_cycle_time) − max(0, review_queue − review_capacity) budget = floor(daily_budget ÷ median_cost_per_item × median_cycle_time) wip = min(clamp(demand, wip_min, wip_max), budget)

The clamp applies after the review-queue penalty, so wip_min stays the floor. The budget line applies last and can go below wip_min, down to 0, because money is a hard limit and WIP is not.

  • accept_rate. PBIs accepted per working day, last 14 days.
  • median_cycle_time. Working days an item holds a WIP slot, summed across its spells between InProgress and Accepted, same window. Time in Sign-off and Needs input is left out, because the item holds no slot there and Little's Law needs W to match what L counts. The budget line uses the same value.
  • review_queue. Factory PRs and scenario sign-offs waiting on a human right now. review_capacity is a config value, default 3.
  • Damping. WIP moves by at most 1 per hour. Lowering it only stops new starts and never kills a running cell. Raising it fills every new slot on the scheduler's next tick, up to the new limit and no further (PBI 177). A WIP override from the dashboard applies at once and skips the damping.
  • Cold start. Until 10 items have been accepted, the factory runs fixed at wip_min.
  • Usage limits. On a subscription, the five-hour and weekly limits bind before dollars do. When an agent hits one, its cell checkpoints and stops, and the scheduler starts nothing new until the reset time the limit message gives. Flow shows limit stalls next to the WIP line. My call
  • Usage reserve. Those limits are shared with your own Claude use, so the factory stops early. When a usage-limit event reports utilization at or above usage_reserve_at, default 0.7, the scheduler starts nothing new until the reset time, and items already running finish. My call
  • Waiting on people. The review_capacity brake in §5 applies in every mode, on top of the formula. The formula's own penalty only shapes the number between those bounds.

Formula first. A model choosing the number on its own can't be audited or reproduced, and that number sets the spend. The formula fits on one dashboard panel. The model still earns its place in advised mode, for things the formula can't see, like a holiday week or a release freeze noted in the backlog. My call

09Safety

  • Untrusted item text. Anyone who can edit a backlog item can plant instructions in it. Agents read item text as requirements to weigh and never as commands. The readiness gate flags items that ask for credentials, CI changes or access outside the repo. On a public repo anyone can also review a factory PR, so a review, and each review comment, steers the factory only when its author maps to an allowlisted user. Anyone else's review requeues nothing. The agent that addresses reviews is handed only trusted authors' comments, checked one by one, because a stranger can reply inside a thread an allowlisted user opened. It gets none of a thread the factory's own review opened, a person's reply in it included, since stage 8 checks and resolves those threads itself, and a review whose only text sits in such a thread requeues nothing (PBI 130).
  • Least privilege. One bot identity per backlog system, with access granted repo by repo and never org-wide. Phase 0 makes one exception, because it dogfoods on a personal account. GitHub documents Project access by GitHub Apps only for organizations, so the factory reaches a personal board with the owner's own gh CLI OAuth token, the owner's decision on 2026-11-06. That token can't be narrowed to the board: gh always asks for at least repo, read:org and gist, and the owner's token also holds admin:org, workflow and user. So in Phase 0 the control plane holds write on every repository the owner can reach, the owner's admin bypass of branch protection, and the power to edit CI workflows. Only the control plane holds it, and cells never see it. It has no expiry, and neither a new gh login nor gh auth logout revokes it, so the control plane's copy outlives both. Revoking it means revoking the GitHub CLI's access in GitHub's settings, which signs out every gh session. A project-only classic token was the narrower option the owner declined. Board edits show as the account owner. The App still does every repo action. Each cell gets a short-lived token for one repo and no production secrets, and never the owner's Claude token. A cell holds a stand-in for its own run and sends model calls to the control plane's model gateway, which checks the stand-in and swaps in the owner's token, so nothing a steered agent writes can carry it. The control plane mints the cell's GitHub token with an explicit permissions set: write on contents, pull_requests and issues, for item comments, and nothing on statuses or checks. Without that set the token gets "all of the permissions that were granted to the app" (GitHub), and a cell steered by planted item text could post a green risk-approval on its own PR. Only the control plane posts that check.

10Failure and recovery

  • Checkpoints. The branch is the checkpoint. Each stage commits its output and the state store records the last stage completed. A new cell picks up from there. A cell stopped mid-stage, by a pause, the kill switch or an operator's stop, commits what its agent left and pushes it as work in progress, then reports the attempt stopped, which uses up none of the stage's retries. It pushes nothing when its lease was lost, since another cell may own the branch, or when the commit changed a locked feature file. The next cell resumes that stage on the branch at that commit and is told to carry on from the work there instead of starting over. A cell the launcher stopped resumes the same way, from its last pushed commit. An attempt the factory closed as stopped because its cell's lease ran out isn't resumed, and the next cell starts that stage over, unless the claim it ended was a restart's (PBI 239).
  • Stale branches. At every claim, before the next stage runs, the cell merges the base branch into the item's branch, because other items may have merged while this one waited. A conflict the agent can't resolve goes to Needs input. The cell fetches the base once per claim, and the check after the agent's pass merges that same commit again. Commits that land on the base while the agent works don't block the item: they reach the branch when the PR conflicts with its base and the item goes back to Queued (PBI 331).
  • Idempotent steps. Opening a PR, commenting and setting status each check current state before acting, so a retry never creates duplicates.
  • Retry budget. Set per stage in the SOP, plus a total per item. When it runs out, the item moves to Failed with a summary of every attempt.
  • Red main. When CI fails on a merge commit on main, the factory compares it with CI on the commit's first parent, the main commit it was merged onto. When a check failed that the first parent passed or never ran, the merge broke main. A check run that was cancelled proves nothing, as when a later push cancelled it, so a check cancelled on the first parent counts as one that never ran there. A merge whose own runs were cancelled and none failed broke nothing, whether CI on it reads as failed or as cancelled (PBI 423): it isn't charged, and it waits on main as below until a later main commit that contains it passes. The item moves to Failed, and the factory files one bug item with the opt-in label. The bug item names the merge commit, the PR and item it came from, each failed check with its URL, and the failing tests where the check's log names them. The scheduler claims it before anything else in the queue, so the factory fixes main before it builds anything more. When the first parent failed the same checks, main was already red and the merge isn't to blame. The item stays Accepted and waits on main, with no Definition of Done failure charged and no second bug item. Once CI passes on a main commit that contains its merge commit, it moves to Done. The one exception is the bug item of a break that still stands. Its merge is the fix for main, so when main is still red after it, the bug item moves to Failed rather than waiting behind itself. The break stays and no second bug item is filed. When main went red with no break the factory recorded, Floor still shows it red, with no item charged and no bug item. If an earlier merge whose CI hadn't reported yet turns out to have broken it, that merge takes the break over: it's charged and files its bug item. A break that has cleared before its bug item is filed, as when filing failed until a later commit on main passed, gets no bug item, since main is already green. While a break stands, Floor says main is red and names the commit that broke it and its bug item, until CI on a later main commit passes (PBI 255). Once that bug item has failed, Floor says main stays red until the bug item is re-queued or someone fixes it. These rules change, and a merge's CI can pass when it's run again, so a merge charged under older rules may not be charged today. #222 is one: it was charged before PBI 255, though its first parent 8d4fe69 failed the same ci check. So every failed_recheck_hours hours, 8 by default, the factory re-checks each item that went to Failed with dod_failed, counting from when it failed or was last re-checked. A re-check runs today's rules on the item's merge commit, the same ones an Accepted item gets. When they no longer say the merge broke main, because CI now passes on it, its only unpassed checks were cancelled, or main was already red, the item moves from Failed to Accepted with the event rechecked. Its board item gets one comment saying why, naming the merge commit and, when main was already red, its first parent. From Accepted it waits on main, or goes to Done, as above. When the rules still say the merge broke main, the item stays Failed, nothing is commented and no second bug item is filed, so a re-check that changes nothing makes no noise. Floor and Run detail show when each such item was last re-checked (PBI 369). My call
  • Quarantine. Three failures in a row on one repo pause that repo and raise a dashboard alert. A streak like that usually means a broken build or a bad SOP change, and the items themselves are fine.
  • Control plane restart. Leases and the event log live in Postgres, so a restart loses nothing. Cells keep running, and the scheduler finds them again through their lease renewals. A planned restart goes through Prepare restart first (§9), so every cell has wrapped up and no cell is running when the factory or Docker stops. Each cell ends its claim at a stage or attempt boundary during the wrap-up. After an attempt that passes, the item goes back to Queued at its next stage (PBI 301). After a failed attempt with retries left, it waits in Queued at the same stage (PBI 393). One stopped by a pause during the wrap-up ends its claim as it exits, even between a stage's end and its transition, so the item goes back to Queued at its stage. A starting control plane or worker clears the restart, and the restarted factory resumes each of those items, starting cells again up to current WIP.
  • New cell code on main. The worker keeps factory-cell:local current with main (PBI 210). As it starts, it records the checkout's HEAD as the commit it started at, since the control plane and the worker run the checkout's files and main is only fetched, never checked out. A worker restarted without a pull may run a commit behind main. It records that commit, with the label of the image the tag names and no restart asked for, before it fetches anything, so a start whose fetch fails still leaves a row that describes this run, and later polls measure main against the commit this worker runs. It then fetches main into the operator's checkout. When main changes no code the control plane or the worker runs compared with that start commit, it builds the image from main's commit. Otherwise it builds nothing, keeps the image there was, and Floor says a restart is needed and names main's commit. On each board poll it fetches main again. When every file changed since the commit it started at is cell-side (sop/, policy/, cell/, src/cell/, except sop/default.yml and src/cell/sop-move.ts, which the control plane and the worker load too, so a change to them needs a restart) or one no process runs (docs, feature files, tests, top-level Markdown), it rebuilds the image from main's newest commit, once, however many commits arrived. The control plane, the worker and every running cell carry on. A running cell keeps the image it started with, and the next cell started runs the new one. When any other file changed, shared code such as src/core/ included, it builds nothing, and Floor says a restart is needed and names main's newest commit, which a restart picks up. The build reads only the fetched commit, written from the checkout's object store into a temporary directory through an index of its own, so the checkout's working tree, index, branch and local commits never reach the image and never block it. Each image the worker builds carries the commit in its org.opencontainers.image.revision label. The start-up image the app host's cell-image resource builds from the checkout (PBI 206) carries HEAD's commit in the same label only when the working tree is clean, and no label when it has uncommitted edits, since that image was built from no commit. Whenever the worker builds nothing, because a restart is needed, or a build fails, it records the label of the image the tag names now, read with docker image inspect, as the commit the image was built from, or none when the image has no label. So Floor never names a commit from an earlier run, whose row Postgres keeps between runs. With no commit known, Floor says the image's commit is not known because it carries no commit label. Each rebuild logs a cell_image_rebuilt event naming the old and the new commit. A failed build keeps the image there was, logs a cell_image_build_failed event with the commit and the error, and is tried again on the next poll.
  • Network blips to GitHub. A cell reaches the outside world through the cell API, which often asks GitHub in turn, and through git push and git fetch against GitHub. One failed try of either no longer ends the attempt (PBI 259). When the cell API answers 5xx, or the connection is refused, reset or gets no answer within 90 seconds, the cell waits and sends the same request again, after 10, 20, 40 and 80 seconds, so 5 tries over 150 seconds. A push or fetch that fails on the network, on a proxy or GitHub 5xx, or on its 10-minute limit is retried the same way. A 4xx answer, such as the 400 for a commit that isn't on the run's branch, and a 409 for a lost lease are never retried, and nor is a git failure that isn't the network's, such as a rejected push. A call still failing after its tries ends the attempt as any other error does, and the attempt's message names the call and says it failed on a network or GitHub error after so many tries. When that call is the fetch of the claim's opening base merge, which runs before any stage, the cell opens an attempt of the stage the run resumes at to carry the message, unless the lease fence has fired. A cell that lost its lease, or failed to renew it 3 times, opens no attempt, since the control plane may be unreachable or another cell may own the run, and the claim ends on the fence's reason, such as the failed renewal, rather than on the network error. When GitHub answers the cell API 5xx or can't be reached, the cell API answers 503 with an error saying GitHub failed, and keeps 500 for its own faults, so the two can be told apart. Every request the factory sends to GitHub, from the cell API, the board client and the repo host alike, has a 30-second limit, and one that runs past it counts as GitHub failing, so a hung GitHub answers the cell 503 well inside its 90 seconds rather than leaving the call to time out. The lease renewal loop renews once a tick and keeps its own tolerance of 3 minutes of failed renewals. The lease fences the retries of a push or fetch: when the cell loses its lease, or fails to renew it 3 times, the retries end and a push or fetch still running is killed, because another cell may own the branch by then. A stop doesn't end them, since a stopped cell still pushes its work in progress. Each retry of a push, the push of work in progress included, checks the lease again first, as the first try does, so a cell that lost its lease while it waited pushes nothing.
  • Lost database connection. When Postgres ends a connection, because an administrator ended it, the server restarted or the network dropped it, the control plane logs it and keeps running. That holds for a connection lost while a transaction or the webhook holds it, as well as for an idle one: the work in flight fails and is logged, and the dead connection is dropped. The pool opens a fresh connection for the next query, so the next scheduler tick and board poll succeed once Postgres is back, and one that runs while it is down fails, is logged and is retried on the next run. The dashboard's live event stream ends its open streams, so each browser reconnects and listens again on a fresh connection.
  • Stuck transaction. A database transaction that never ends, such as one holding a lock it never releases, can stall the scheduler, the board poller or a cell's request to the cell API without an error, so nothing fails and nothing would be logged. Long-running work speaks up instead. A scheduler tick or a board poll still running after 5 minutes logs how long it has run and the step it is in, and logs again every 5 minutes until it ends. A cell API request still open after 60 seconds logs its route and run id. The warning only reports the stall. It doesn't cancel the work, so a person reading the log finds the stuck step and ends the transaction behind it. The factory logs rather than leaning on a database timeout, because statement_timeout and idle_in_transaction_session_timeout act through the backend's interrupt check, which a backend stuck this way never reached, so neither would have ended the stall.
  • Hung model call. An upstream model service can take a request and never answer it. The cell waits with no error, and the gateway holds no row lock, so the stuck-transaction warnings never see it. A model request whose upstream hasn't sent its response headers 60 seconds after the model gateway forwarded it logs its path and the same run id the cell API's slow line names, once, so a stuck model call looks different from a working agent. The gateway times only the wait for headers, because a healthy stream can run well past 60 seconds. The headers, an upstream error or the cell disconnecting end the watch, so a stream that started in time stays quiet however long it runs (PBI 154). Like the other warnings, it only reports the stall and cancels nothing.

Local run

Phase 0a runs the whole factory on the owner's machine before any Azure resource exists. An Aspire app host, apphost.mts, starts every dependency with aspire run. Yours for local-first, My call for the details below.

  • Dependencies. Postgres and the Azurite storage emulator run as Aspire container resources with data volumes. A container with the default lifetime is disposed of when the app host stops (aspire.dev), so the volumes are what let a restart keep every item, run and event. A one-shot migrate resource applies the schema and upserts the board and the dev owner. The control plane runs as a Node process and starts only after migrate exits, through the app host's waitForCompletion (aspire.dev). Secrets arrive as Aspire secret parameters, set from user secrets or Parameters__<name> environment variables with each dash written as an underscore (aspire.dev). The dashboard asks for any parameter with no value and can save it to user secrets. The one exception is the GitHub App key, which arrives as the path to its .pem, because the dashboard's one-line form drops a pasted key's line breaks (issue #207).
  • Start checks. Before any resource starts, the app host itself pulls and brings Docker up, so aspire run from the repo root is the one command that starts the factory (PBI 205, PBI 208). The npm run factory script that used to run these checks first is gone. On main it runs git pull --ff-only, so control, the worker and migrate run the code it pulled. A pull that fails, because main has diverged, local edits would be overwritten or the remote can't be reached, stops the start with git's own message, and no resource starts. On any other branch, or a detached commit, it warns that it runs the checkout as it is and pulls nothing. When docker version doesn't answer, it launches Docker Desktop and waits up to 3 minutes, asking again every 3 seconds, and stops with "Docker did not come up within 3 minutes." if it never answers. With Docker Desktop not installed where it looks, it stops with "Docker is not running, and Docker Desktop is not installed where this looks. Start Docker first." A test run, with FACTORY_FLOAT_PORTS=1 as the BDD suites start the app host, pulls nothing and runs no git, so a suite run on main never moves the checkout or waits on a credential prompt. It still checks Docker. aspire publish starts nothing, so it skips both checks.
  • Cell image at start. The egress proxy and every cell run factory-cell:local, so under aspire run the app host builds it itself, as a resource named cell-image in the Aspire dashboard (PBI 206). Like every resource it starts only after the start checks, so on main it builds the commit the pull brought in, and on any other branch the checkout as it is, uncommitted edits included. It runs docker build on the checkout with the checkout's own cell/Dockerfile, and labels the image with HEAD's commit only when git status --porcelain is empty. It builds on every start, even when an image is already there. The worker waits for cell-image to complete with exit code 0. A build that fails, Docker going away included, shows cell-image as failed with Docker's output in its console, leaves the image there was, and the worker never starts. Once the worker runs, it keeps the image current with main as the item above says.
  • Cells. The control plane starts each cell as a Docker container, from an image built for the machine's own architecture and never pushed. Cells reach the control plane and Azurite through Docker Desktop's host.docker.internal, so local upload URLs carry that host. The launcher gives a cell the model gateway's URL and a stand-in token for its run, never the owner's Claude token (§9). A Linux container keeps the cell's runtime and run: commands the same as in Azure. The sandbox is the exception: bubblewrap can't create a namespace in a cell container under Docker Desktop, so a sandboxed cell runs no Bash command at all. The owner chose to enforce the allowlist with the network instead. Cells join an internal Docker network, which "Containers on an internal network may communicate between each other, but not with any other network" describes (Docker). The same page adds that the network's gateway, and host services set up to listen there, stay reachable. A probe from an internal network found nothing answers there. Aspire's ports, bound to 127.0.0.1, refused the connection. Ports that other containers publish on every interface timed out. The egress test checks both kinds. A cell's one way out is a proxy container on that network and on the default bridge network, which admits only the allowlisted hosts plus the local control plane and storage emulator. The proxy lets through any request to the storage emulator that carries a SAS, so the emulator must not accept a SAS signed with Azurite's published devstoreaccount1 key. Under aspire run it runs on a random key that the app host draws at each start and hands to the control plane in FACTORY_BLOB, so a SAS a cell signs for itself gets 403 (PBI 84). Cells reach the proxy through HTTPS_PROXY, which Claude Code supports (Claude Code). The SDK sandbox stays off locally. A cell has no Docker daemon, so each test that needs a database starts its own Postgres server inside the cell, from binaries in the cell image. A cell runs the database suites and the @db scenarios as CI does. Scenarios that need the owner's machine, with Docker, Aspire and the real secrets, run in neither, so the owner runs them and the PR records the run.
  • Intake. GitHub can't reach a local machine, so the App's webhook stays off and the poller does all intake, closed PRs included. Sign-off and answers happen in the local dashboard, and comment commands wait for Azure's webhooks.
  • Sign-in. There is no built-in auth locally, and cells reach the same port. So the control plane prints a one-time sign-in link at each start, and only a browser holding the cookie it sets is the dev user. Every dashboard POST must come from the dashboard's own origin, the address the browser uses, locally and in Azure. Locally that's the address of Aspire's proxy in front of the control plane, which the app host passes in, not the port the control plane listens on behind it. The control plane refuses to start with a dev identity outside local mode, or inside any Azure container app. The app host sets local mode only for aspire run, and Azure never sets it.
  • App host language. The app host is TypeScript, like the rest of the repo. Aspire 13 scaffolds it with aspire init --language typescript (aspire.dev). The docs give it no stability label, so the first local run checked it, and it carried every resource above with no C# fallback needed (docs/superpowers/spikes/2026-11-local-platform.md).

Transcripts while a stage runs. A stage's transcript doesn't wait for the stage to end. While a stage runs, the cell uploads the transcript so far, every message its agent calls have written, to the attempt's usual path. It does so at most every 15 seconds, and only when new messages have arrived since the last upload that worked. Run detail links the transcript from the first upload, and the link shows everything up to the latest upload. Tokens and cost for a running stage stay 0 until the stage ends. When the stage ends, passed, failed or stopped, the cell waits for any upload still under way, then uploads the complete transcript to the same path.
