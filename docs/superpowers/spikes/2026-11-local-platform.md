# Local platform spike

Plan Task 2, run on 2026-11-06 on the owner's machine: Windows 11 on ARM64, Docker Desktop with a `linux aarch64` 29.7.2 daemon, Aspire CLI 13.6.4 and Node 26.13.0. These results come from `aspire start`, `aspire describe` and `docker run` against `factory-cell:local`. Each line gives what the plan expected, then what happened.

## Results

- **AppHost.** Expected every resource in Task 2 Step 3 to come up. It did: `aspire start` brought up `pg`, `storage`, `migrate` and `control`, and `aspire describe migrate --format Json` reported `"exitCode": 0`. The TypeScript AppHost needed no C# fallback.
- **Data volumes.** Expected named volumes on Postgres and Azurite. `aspire describe` reports `aspire-managed-995a72394f-pg-data` and `aspire-managed-995a72394f-storage-data` as `volume` mounts on the two containers. The probe's run count also went up by one across a stop and a start, so the Postgres volume kept its rows.
- **Database variable.** Expected a database connection on both apps. `migrate` and `control` receive `FACTORY_DB_URI`, a `postgresql://` URI built from the database's `uriExpression()`.
- **Blob variable.** Expected the blob connection on `control`. It receives `FACTORY_BLOB`, the Azurite connection string. Its blob endpoint is `localhost` on a port Aspire picks, 53133 on this run, and not the 10000 the plan first assumed.
- **Secret variables.** Expected the secrets on `control`. It receives `CLAUDE_CODE_OAUTH_TOKEN`, `GITHUB_APP_KEY`, `GITHUB_PROJECT_TOKEN`, `CELL_SECRET` and `GITHUB_WEBHOOK_SECRET`, plus `GITHUB_APP_ID` and `CLAUDE_TOKEN_CREATED_AT`. `GET /probe/env` lists their names, never their values.
- **Installers.** Not planned for. Each Node app gets its own `npm install` resource. With both apps in the repo root, the two installs collided with `EBUSY`, so `control` skips its install and waits for `migrate`, whose install runs first.
- **Cell to control plane.** Expected 204. `curl -X POST http://host.docker.internal:7400/internal/cells/ping` from `factory-cell:local` got 204.
- **Cell to Azurite.** Expected 201. A PUT to a `/probe/sas` URL with its host name swapped to `host.docker.internal` got 201, so the SAS signature doesn't cover the host.
- **Agent SDK.** Expected `subtype` "success". `spike/sdk-oauth.ts` in `factory-cell:local`, with `CLAUDE_CODE_OAUTH_TOKEN` passed by name, returned "success" on `claude-haiku-5-5`. So the `claude -p` fallback isn't needed.
- **Bubblewrap.** Expected it to start. It doesn't start in a local cell container: `bwrap --ro-bind / / --dev /dev true` fails with "Creating new namespace failed: Operation not permitted", under the default `docker run` and with `--security-opt seccomp=unconfined` too. The egress allowlist needs another mechanism locally, and on 2026-11-06 the owner chose an allowlisting proxy on an internal Docker network, which Task 13 builds.
- **Internal network.** Expected no way out but the proxy. A `factory-cell:local` container on a throwaway `--internal` network, gateway `172.21.0.1`, got curl exit 7, "couldn't connect", for Azurite, Postgres and the control plane on the gateway IP, because Aspire binds every published port to `127.0.0.1`. A second probe tried three ports that other containers on this machine publish on `0.0.0.0`: an Azurite on 29293, a Key Vault emulator on 30473 and hydra on 14444. Each got curl exit 28, a timeout, on the gateway `172.20.0.1`, so that traffic is dropped, not answered. The cause is most likely Docker's isolation rules for internal networks, which this probe doesn't prove. The first probe also got curl exit 6, "couldn't resolve host", for `host.docker.internal`, `example.com` and `api.github.com`, because Docker gives an internal-only network no outside DNS. So a cell reaches the control plane and storage only through the proxy, which sits on the default bridge and can resolve `host.docker.internal`.
- **Sandbox probe.** Expected example.com blocked and api.github.com allowed. Neither request ran. `spike/sdk-oauth.ts sandbox` returned "success", but both `curl` commands failed inside the sandbox with `bwrap: No permissions to create new namespace`. The agent then tried to run outside the sandbox, and the permission gate refused it with "Run outside of the sandbox". So the sandbox fails closed: no request leaks, and no Bash command runs. The agent's own suggested cause is that the Docker Desktop VM's kernel doesn't allow unprivileged user namespaces, which is unverified.
- **GitHub App.** Expected an App with the Task 2 Step 5 permissions. `ricksu978-software-factory`, App id 5636555, came from the manifest flow with write on contents, pull requests and issues and read on checks, commit statuses and metadata. It's installed on this repo only, as installation 179116800. Its private key and webhook secret sit in the AppHost's user secrets, never in the repo.
- **Bot assignment.** The plan left it open. GitHub refused it: assigning `ricksu978-software-factory[bot]` to issue #6 with an installation token holding issues write got 403 "Forbidden", and the assignees stayed empty. So Task 6's claim marker is the `factory:in-progress` label alone.
- **Model gateway.** Added after issue #33, which found that a cell holding the owner's Claude token could leak it. Expected the agent to work with only a stand-in token. A throwaway gateway ran on a private Docker network with no published ports, holding the real token, and a `factory-cell:local` container on that network ran `spike/sdk-oauth.ts` with `ANTHROPIC_BASE_URL` pointing at the gateway and `CLAUDE_CODE_OAUTH_TOKEN` set to a fake `sk-ant-oat01-` value. It returned `"subtype":"success"`. The gateway logged three requests, `HEAD /api/hello` and `POST /v1/messages?beta=true` twice, all 200. The cell's own `anthropic-beta` header carried `oauth-2025-04-20`, so the gateway forwards it unchanged and adds nothing. Those paths became the gateway's allowlist, plus `/v1/messages/count_tokens`.
- **Board token.** Expected a `project`-only classic token. The owner chose their `gh` CLI OAuth token instead, which also carries `repo`, `admin:org` and `workflow`. Spec §9 records that decision and its cost.

## Egress first run

Plan Task 13, run on 2026-11-06 on the same machine, Docker server 29.7.2 on `linux/arm64`. `ensureEgress` from `src/scheduler/launcher.ts` ran for real with `CELL_CONTROL_URL` set to `http://host.docker.internal:7400` and a blob endpoint on 7410. The probes ran in `factory-cell:local` containers on `factory-cells` with the four proxy variables and `NODE_USE_ENV_PROXY=1`. `aspire run` wasn't running, so a throwaway Node server on `127.0.0.1:7400` stood in for the control plane and answered 204 to `POST /internal/cells/ping`.

- **Proxy choice.** A small Node proxy, `src/scheduler/egress-proxy.mjs`, which admits exact `host:port` pairs: CONNECT for the three HTTPS hosts on 443, and plain HTTP forwarding for `host.docker.internal` on the two pinned ports. Anything else gets 403. Tinyproxy can't express that. Its `ConnectPort` is one global list of ports, its filter matches domains by default, and URL filtering "works only in plain HTTP scenarios" ([tinyproxy docs](https://tinyproxy.github.io/)). The docs give no way to admit `host.docker.internal` on two ports and refuse it on the rest. The proxy runs from `CELL_IMAGE` with `--entrypoint node`, so it needs no image beyond the one cells already use. The label hashes the image name, the allowlist and the script's text.
- **Two networks.** `docker run` accepted `--network bridge --network factory-cells` together, so the proxy joins both networks in one step and never runs on only one.
- **Boot.** The first `ensureEgress` created the internal network, gateway `172.20.0.1`, and started `factory-egress` on `bridge` and `factory-cells`. A second call with the same configuration kept the same container id and start time. A call with the control port changed to 7401 replaced it, and the next call with 7400 replaced it again. One `factory-egress` remains, with the 7400 label.
- **Name resolution.** `getent hosts factory-egress` in a cell returned `172.20.0.2`, so the internal network's DNS resolves the proxy by name.
- **Allowed hosts.** `curl https://api.github.com`, `https://github.com` and `https://registry.npmjs.org/` each got 200 through the proxy.
- **Refused hosts.** `https://example.com`, `https://api.anthropic.com` and `https://platform.claude.com` each failed with curl exit 56, "CONNECT tunnel failed, response 403". So did `https://140.82.112.6`, a GitHub IP, because the allowlist holds names. Plain `http://example.com` and `http://api.github.com` on port 80 got 403.
- **Host ports.** `curl -X POST http://host.docker.internal:7400/internal/cells/ping` got 204 from the stand-in server, which logged the request with `Host: host.docker.internal:7400`. Port 5432 got 403 as plain HTTP and as a CONNECT tunnel. A PUT to 7410, which is allowed but had no Azurite behind it, got 502, so the proxy forwarded it.
- **Node fetch.** Node 26.13.0 sent `fetch` through the proxy under `NODE_USE_ENV_PROXY=1`. `fetch("https://api.github.com")` got 200, which it can't reach without the proxy, and `fetch("https://example.com")` failed. So the cell's API client needs no explicit proxy agent.
- **No proxy.** With the four proxy variables unset, `curl https://api.github.com` and `curl http://host.docker.internal:7400` both got curl exit 6, "Could not resolve host". On the gateway IP, ports 7400 and 80 got curl exit 7, refused. Ports 29293 and 14444, which an Azurite and hydra publish on `0.0.0.0`, timed out with curl exit 28.
- **Launcher.** `dockerLauncher` started a `factory-cell:local` container with a sample cell env and returned its id. The image's command is still `node`, so it exited at once and `--rm` removed it, and `stop` then treated "No such container" as stopped.
