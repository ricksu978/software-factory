# Software Factory Phase 0 Implementation Plan

> **For agentic workers.** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal.** Build the Phase 0 walking skeleton from spec §13, in two stages. Phase 0a, Tasks 1 to 18, runs it on the owner's machine under Aspire. Phase 0b, Tasks 19 and 20, moves it to Azure. One personal GitHub repo, which is this repo, and one personal Project as its backlog, fixed WIP of 1, SOP stages 1 to 7 plus a thin stage 8 that addresses review feedback. A person merges and the item reaches Done once CI on main is green. The risk classifier runs in shadow mode, and the dashboard has Floor with its three strips, Run detail and five overrides: pause, drain, stop a run, hold an item and re-queue one.

**Architecture.** One TypeScript codebase with two entry points. The control plane runs the watcher, scheduler, dashboard and cell API in one process: a Node process under Aspire in Phase 0a, and a single always-on Container App in Phase 0b. A cell runs once per PBI, as a local Docker container in Phase 0a and a Container Apps job execution in Phase 0b, and drives the Claude Agent SDK through the SOP stages. Cells never touch Postgres. They talk to the control plane's cell API with a per-run token fenced by the lease generation. Postgres is the only state store, and every state change appends to the `event` table.

**Tech Stack.** Node 26.13.0 LTS running `.ts` files directly through type stripping, `node:test`, TypeScript 7.0.2 for type checks only, `pg` 8.23.1, `yaml` 2.9.1, `@anthropic-ai/claude-agent-sdk` 0.3.318, `@octokit/app` 16.1.4, `@azure/identity` 4.14.1, `@azure/arm-appcontainers` 4.0.0, `@azure/storage-blob` 12.34.0, `@testcontainers/postgresql` 12.2.1, `@cucumber/cucumber` 13.3.0 for the Gherkin runner, `@types/node` 26.6.6 and `@types/pg` 8.23.1 for the type check, Bicep for infrastructure.

**Spec.** `docs/superpowers/specs/2026-11-05-software-factory-design.html`, as revised on this plan's branch with the 14 flow-review fixes. §13's Phase 0 row is the scope. §14 lists the settled decisions this plan does not reopen.

## Global Constraints

- Phase 0a runs locally. `aspire run` on `apphost.mts` starts:
  - Postgres;
  - the Azurite storage emulator;
  - a one-shot `migrate` resource;
  - the control plane as a Node process.

  Cells run as Docker containers that the control plane starts from `factory-cell:local`, built for the machine's own architecture and never pushed. GitHub can't reach the machine, so the poller does all intake. Sign-in is a dev identity that only `FACTORY_ENV=local` accepts. Postgres and Azurite keep their data in Aspire data volumes, so stopping `aspire run` loses nothing. Docker Desktop must be running.
- Phase 0b, in Azure: region australiaeast. Control plane is one Container App at 0.5 vCPU and 1 GiB with external ingress. Cells are a Container Apps job, manual trigger, 2 vCPU and 4 GiB per replica, retry limit at least 1.
- Azure images are `linux/amd64` and build in CI. No image built on the ARM64 dev machine is ever pushed. The local `factory-cell:local` image is the one native build, and it never leaves the machine.
- In Azure, Postgres is a Flexible Server, Burstable B1ms, with Microsoft Entra authentication through managed identities and no stored password.
- Transcripts go to Blob Storage, Hot LRS in Azure and Azurite locally, and `stage_run.transcript_ref` points at them. In Azure, container logs go to Log Analytics.
- Key Vault holds the GitHub App private key and the Claude OAuth token in Azure, and Aspire secret parameters hold them locally. Cells never hold the Claude token. Each gets a stand-in for its run and sends model calls to the control plane's model gateway, which swaps in the real token (issue #33). Cells never run with `--bare`.
- Model IDs live in the SOP file only: `coding: claude-opus-5-5`, `triage: claude-haiku-5-5`.
- Phase 0 dogfoods: the target repo is this repo, `ricksu978/software-factory`, owned by a personal account, and the backlog is a Project on that same account. The GitHub App, installed on the account, does all repo work. The board is reached with the owner's `gh` CLI OAuth token, because GitHub documents Project access by GitHub Apps only for organizations. That token is far broader than the board, which spec §9 records as the owner's decision. Board edits therefore show as the account owner, and board changes arrive only through the 5-minute poll, since `projects_v2_item` webhooks are organization-only. This is a Phase 0 exception to spec §9's one-bot-identity rule, decided 2026-11-06. An org-owned board can replace it later without code changes, through the adapter's `owner` setting.
- Eligibility label `factory`. Quality criteria live in the repo's policy files, per Run contract 11. A repo with no `.factory/dod.md` fails readiness for every item.
- Poll every 5 minutes, on top of webhooks in Phase 0b. Leases renew every 60 seconds and expire after 5 missed renewals. A cell stops itself after 3 minutes of failed renewals.
- `lease_generation` changes only as Run contract 2 says. A cell checks its generation before every push, comment and state write.
- NeedsInput and SignOff items get reminders at day 2 and day 4, and move to Abandoned after 5 days with no answer. An operator re-queue or a late answer brings an Abandoned item back.
- The scheduler starts nothing new while the waiting count (Run contract 3) reaches `review_capacity`, default 3, or while the last reported usage utilization is at or above `usage_reserve_at`, default 0.7.
- The factory owns board status. The project's built-in status workflows are off, factory PRs reference their item with `Refs #n`, and the factory closes the item at Done.
- Sign-off (`/approve`, `/changes <note>`) and answers (`/answer <text>`) are accepted in Run detail. In Phase 0b, once webhooks arrive, they are also accepted as item comments from GitHub logins mapped to allowlisted users.
- An override takes effect within 30 seconds. The kill switch stops every cell within a minute.
- Cell GitHub tokens are minted with explicit `permissions`: write on `contents`, `pull_requests` and `issues`, and nothing on `statuses` or `checks`.
- Phase 0 runs WIP fixed at 1, SOP stages 1 to 7, a thin stage 8, and the risk classifier in shadow mode. The thin stage 8 runs `factory-pr-reviewer` on the factory's own PR before people look (PBI 128), and `pr-addresser` on the reviewer's findings, on requested changes and on merge conflicts. Shadow mode records a tier on every PR and posts no `risk-approval` check.
- A merged item reaches Done once CI on main is green for the merge commit, so the target repo's CI runs its scenarios. Stage 10's post-merge verification, stage 11, budget caps, Inbox, Cost view and quarantine belong to Phase 1.
- In Phase 0b, sign-in goes through Container Apps built-in auth with Microsoft (any Entra directory and personal accounts) and Google. Phase 0a uses the dev identity from Task 15. In both, the app's own `user` table decides access, and roles are viewer, operator and owner.
- A cell has no Docker daemon, so it can't start a Testcontainers database. Test files that need a database use `dbTest` from `src/store/test-db.ts`, which skips them when `FACTORY_DB_TESTS=skip`, and scenarios that need one carry `@db` (Task 4). Until PBI 22, this repo's `.factory/dod.md` and `.factory/config.yml` set that variable and filtered `@db` out of `bdd.run`, so cells skipped both. PBI 22 gives every test its own Postgres inside the cell (below), and from then on `.factory/` sets neither, so a cell runs the database suites and the `@db` scenarios as CI does (Run contract 6). Scenarios that need the owner's machine carry `@local`, which cells and CI both skip (Task 4).
- **A database in every test, inside the cell (PBI 22).** The cell image carries the Postgres 17 server binaries from the PostgreSQL apt repository, the version `startTestDb` uses in CI, with Debian's default `main` cluster turned off in `/etc/postgresql-common/createcluster.conf`. The image sets `FACTORY_PG_BIN` to `/usr/lib/postgresql/17/bin`, which isn't on `PATH`. With that variable set, `startTestDb` starts no container. It starts its own server instead, the same way Testcontainers gives each call its own (Task 4):
  - `initdb --auth=trust` in a fresh temp directory;
  - `pg_ctl start -w` with `listen_addresses=''` and `unix_socket_directories` set to that directory, so the server listens on no TCP port at all;
  - `stop` stops the server and deletes the directory.

  `initdb` refuses to run as root, and the cell runs as the non-root `factory` user that Task 14 Step 6 adds. The engine's `commandEnv` (Task 14) passes `FACTORY_PG_BIN` to every gate command, per Run contract 11. The variable names only a path inside the image, so it carries no secret. Run contract 5's cell env is unchanged, and Run contract 11's env for the gates' commands gains `FACTORY_PG_BIN`, because that env passes nothing else from the image. PBI 22 then drops `FACTORY_DB_TESTS=skip` and the `not @db` filter from `.factory/dod.md` and `.factory/config.yml`. An item with an `@db` scenario no longer fails Red with "not run in the cell".
  - **Two cells, or two test files in one cell.** Every `startTestDb` call has its own server, so nothing is shared: no rows, no database, no roles. A role a test creates, such as `id-factory-control`, dies with its server, as under Testcontainers. One shared server per cell would not do, because roles span a whole server and `migrate`'s advisory lock spans one database, so parallel files would race on `create role factory_app`.
  - **Who runs them.** The engine runs `commands.test`, `bdd.run` and every `dod.md` command itself, through `sh -c` outside the agent's sandbox (Run contract 11), so the gates always reach their servers. A test the agent runs from its own Bash may sit inside the sandbox where Azure turns it on, and Task 19 Step 9 checks whether it can still start a server there.
  - **The factory's own database.** Locally it is Aspire's `pg` container. A cell sits on the internal `factory-cells` network, and the egress proxy refuses every Postgres port (Task 13), so the cell can't reach it. In Azure the Flexible Server admits Azure services, which include the cell job, so a cell can reach it over the network. There the guard is authentication: the server takes Entra tokens only, the cell job carries only `id-factory-cell`, and that identity has no Postgres principal (Task 19). That is weaker wording than "can reach only its test database" in PBI 22's third criterion. Closing the network path too needs the server on a private VNet, which Phase 0 doesn't buy.
- This repo is public, decided 2026-11-06. On the Free plan that's what makes branch protection and deployment environments with required reviewers available ([GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)). `main` takes changes only through a PR with one approving review and a green `lint` check, and refuses force pushes and deletions. Admins bypass every one of those rules, because `enforce_admins` is off and "the restrictions of a branch protection rule do not apply to people with admin permissions" by default ([GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). That lets the owner merge their own PRs, which GitHub won't let them approve. The factory's App holds no admin or bypass rights, so a cell's push token can't write to `main`. Task 1 adds its CI job to the required checks, and Task 19 adds the `production` environment.

## Review Focus

1. **Planted instructions in PBI text.** An item body that asks for secrets, CI changes or access outside the repo is flagged NotReady by the gate, and no cell token can post a status or check. Tests in Task 9 and Task 7.
2. **Zombie cell after lease expiry.** An old cell whose lease was re-claimed gets 409 on every cell API write, so it can't push, comment or move state. Test in Task 12.
3. **Duplicate or replayed webhook deliveries.** The same `X-GitHub-Delivery` id processed twice yields one event. A bad or missing signature yields 401 and no event. Tests in Task 7.
4. **Spoofed identity headers.** A request that carries `X-MS-CLIENT-PRINCIPAL` on an auth-excluded path never authenticates a dashboard action, and an unknown signed-in subject gets the no-access page. Tests in Task 15, plus a live check in Task 19.
5. **Control plane restart mid-run.** A fresh scheduler process sees the running cell's live lease and starts no second cell for that item. Test in Task 13.

## Run contract

These rules hold across every task. A task that touches one of them follows this section and does not restate it.

1. **Resume pointer.** `run.next_stage` names the stage the next cell runs, and the scheduler passes it to the cell as `RESUME_FROM`. These are its only writers:
   - `/stage` with `passed` sets it to the next stage in the pinned SOP;
   - a passed `specify` leaves it at `sign-off`, which no cell runs;
   - `decide` sets it to `red` on approve, and to `specify` on changes;
   - `changes_requested` sets it to `address`;
   - `pr_opened` sets it from `address` back to `open-pr`, where an InReview item's pointer stands, because the address run that sent it has finished its work (PBI 191);
   - `requeued` sets it to `open-pr` when `prState` reports the run's PR closed without a merge, so `openOrUpdatePr` opens a fresh PR from the kept branch;
   - a new run starts it at `understand`.
2. **Leases and generations.** `lease_generation` goes up by 1 exactly twice in a lease's life: when a claim moves an item into InProgress, and when any transition moves an item out of InProgress. The second bump fences the old cell, so its next cell API call gets 409. Leaving InProgress also clears `lease_owner` and `lease_expires`. `expireLeases` looks only at InProgress items. No other transition touches the generation.
3. **Waiting on people.** The waiting count is the number of SignOff and NeedsInput items whose question is still unanswered, plus every InReview item. Answered and Abandoned items don't count. The brake gates only claims that start new work: a Queued item with no open run, or whose open run has no `stage_run` row yet. Every other claim resumes work already in flight and is never gated. That covers an answered SignOff or NeedsInput item, and a Queued item back from `changes_requested`, `lease_expired`, `usage_limited` or a late answer. So answering never deadlocks the line, and an address run never waits behind the brake.
4. **Item scope.** Specify tags every feature file it writes with `@pbi-<externalId>` at Feature level.
   - `redGate` and `traceability` consider only scenarios carrying that tag. Among them, `redGate` needs a `@regression` scenario green rather than red (Task 10).
   - `greenGate` requires every scenario in the suite to be green, which keeps earlier items' scenarios as regression tests.
   - At sign-off, `run.locked_files` records the files carrying the tag, and `matchesLock` diffs only those files. So other items merged into the base never trip the lock.
5. **Cell context.** The cell's env holds only `RUN_ID`, `ITEM_ID`, `GENERATION`, `RUN_TOKEN`, `CONTROL_URL` and `RESUME_FROM`, plus the two model variables from `cellModelEnv` in `src/control/model-gateway.ts`. The scheduler passes the six. `ANTHROPIC_BASE_URL` points at the control plane's model gateway, `<CONTROL_URL>/internal/model`, and `CLAUDE_CODE_OAUTH_TOKEN` holds a stand-in, `sk-ant-oat01-<runId>.<generation>.<runToken>`, never the owner's token (issue #33). The gateway checks the stand-in the way the cell API checks a run token, so a leaked stand-in reaches only the gateway's allowlisted model paths and dies with the run's generation. In Azure the gateway is on public ingress, so until then it works from anywhere. Locally `dockerLauncher` also adds the egress variables from Task 13: the proxy variables and `NO_PROXY` in both cases, `NODE_USE_ENV_PROXY`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` and `ENABLE_CLAUDEAI_MCP_SERVERS`. None of them carries a secret. Everything else comes from `GET /internal/cells/:runId/context`:
   - the item's external id, title and acceptance criteria;
   - `nextStage`;
   - the latest decision or answer, with its note;
   - `lockSha` and `lockedFiles`;
   - `prNumber`, `repo`, `base` and `branch`;
   - `configSha` and `sopVersion`;
   - `dodVerdicts`, the latest `dod.md` verdicts from `policy_result`, so a cell resumed at open-pr still gives the classifier the `person` lines, and `dodCheckedSha`, the commit they were checked at;
   - `scenarioNotes`, from `run.scenario_notes`, the approving self-review round's `SCENARIO NOTE:` lines, so an open-pr in a later claim, after a usage limit, a stop, an answered block or a requeue, still writes them into the PR body (PBI 152);
   - `trustedComments`, for an address run, under Run contract 10;
   - `stageAttempts`, the highest attempt in `stage_run` per stage, so a later claim on the same run numbers its attempts on from there and writes over no earlier row or blob;
   - `resume`, which is `{ stageId, attempt }` when the last attempt at `nextStage` is `stopped`, and null otherwise (PBI 140). The cell then carries on from the work in progress that attempt pushed.
6. **CI status.** Only the control plane reads checks, with the App's own `RepoHost`. The cell reports its PR through `POST /pr` as soon as the PR exists. After every push, the cell asks about the exact commit it pushed with `GET /internal/cells/:runId/checks?sha=<sha>`. The control plane polls the checks on each sha it has been asked about, and on every merge commit. A sha with no checks reported 10 minutes after the control plane first saw it returns `none`. A sha CI failed on returns each failed check's name, URL and the last 100 lines of its log, read by the control plane, so the cell learns why CI failed without GitHub access (PBI 232). The engine treats `none` as `blocked`, with "no CI ran on the PR". Phase 0 requires CI on the target repo. Cell tokens keep the permissions in Global Constraints. The cell's own repo calls go through `cellRepoHost`, which opens PRs and requests reviewers with the token from `/github-token`.
7. **Branches and runs.** A run's branch is `factory/pbi-<externalId>-r<runNumber>`. These start a new run on a new branch from the base:
   - `criteria_changed`;
   - a re-queue of an item whose PR already merged.

   The previous PR, if still open, is closed with a comment that names the kept branch.
8. **Board mirroring.** One `onTransition(itemId, from, to, event)` hook runs after every committed transition.
   - It writes `fieldMap.statusFor[to]` through `setStatus`. A null entry leaves the board's status as it is.
   - It calls `claim` on every move into InProgress, which is idempotent, so a revived item gets its marker back. It calls `release` on reaching Done, Failed or Abandoned, and `linkPr` on `pr_opened`.
   - It closes the item at Done.
   - Whenever an item with an open PR reaches Abandoned, through `withdrawn` from any state, the PR is closed with a comment that names the kept branch. The poller already closes it when it withdraws an item (Task 8), so the hook skips a PR that's no longer open.
9. **End-of-stage order.** A stage ends with these calls in this order: `/stage` with `passed`, then every `/upload-url` upload, then `/pr` when the stage opened a PR, and the `/transition` last. The transition is the call that raises the generation, so any call after it would get 409. A stopped attempt (PBI 140) sends its uploads first and `/stage` with `stopped` last, because during a restart that report ends the claim and raises the generation too. Its row already exists from its `started` report.
10. **Review triggers.** Requested changes count only when a review from an allowlisted login was submitted after `run.reviews_seen_at` and either requests changes or leaves a comment in a thread that is still unresolved. The second case covers a review that only comments, such as the PR reviewer's, whose findings are inline threads. A resolved thread asks for nothing. A thread the factory's own review opened, whose first comment is by the repo's `trusted_bot` as `botKey` names it, asks for nothing either, whoever replies inside it: it belongs to the pr-review stage, which checks and resolves it itself. The poller passes the repo's `trusted_bot` to `prState`, which skips those threads (PBI 130). For the same reason a review that requests changes counts only when it has a summary or a comment outside the factory's threads. One whose only text is a reply inside a factory thread would hand the address run nothing to read, and the run would block. `prState` matches each thread comment to its review by the review's `databaseId` (PBI 130). A thread comment counts only once it has stood two minutes. A reviewer posts a verdict reply and then resolves the thread, and a poll between the two would send the item to address with nothing left to read, which blocks it under issue #28's third criterion. Past those two minutes, any trusted reply on an open thread counts as a new review, so a "thanks" left open starts one more address run. A thread whose only trusted comments predate the last address claim never fires again, so a reviewer who still finds it unfixed has to reply in it or review again. Two writes set that column:
    - `POST /pr`, when the cell records the PR in the open-pr stage. A retried open-pr attempt records it again and keeps the clock. The PR is open on GitHub while the factory's own PR review runs and the item is still InProgress, so a trusted review left then counts, and it sends the item to address on the first poll after the item reaches InReview (PBI 191). A `pr_opened` with no `POST /pr` before it starts the clock instead;
    - the claim that starts an address run, set to that claim's time.

    A review left while address is running is newer than the claim, so the next poll still catches it once the item is back in InReview. The webhook compares a changes-requested review's `submitted_at`, and only for a review with a non-empty summary. Its payload carries no line comments, so it can't tell whether a review with no summary holds anything outside the factory's threads, and leaves that review to the poll (PBI 130). The poll compares the newest such review from `prState`, which reads each open thread comment's review time over GraphQL, so only the poll catches a review that only comments. GitHub's aggregate `reviewDecision` isn't used, because it can stay `CHANGES_REQUESTED` after the fix is pushed.

    **Trusted reviewers.** The repo is public, and "Anyone with read access can review and comment on proposed changes" ([GitHub](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)). So a review, and each review comment, counts only when its author's login is the `github_login` of an allowlisted user, the same rule item comments follow. Trust is per comment, because anyone can reply inside a thread a trusted reviewer opened. An untrusted review requeues nothing. `GET /context` gives an address run `trustedComments`, the comments in unresolved threads written by trusted authors or by the App's own bot user, with their thread, path, line and body. A thread the factory's own review opened is left out whole, a trusted reply inside it included, through `withoutFactoryThreads` in `src/adapters/types.ts` (PBI 130). A reviewer can also request changes with only a top-level summary. A summary can't be resolved, so it joins the list while its author's latest review, not counting reviews that only comment, requests changes, as in GitHub's own reviewer state. It has the review's id as its thread and no path or line, and the same author rule applies to it (issue #28). Logins match as GitHub compares them, ignoring case, through `loginKey` in `src/adapters/types.ts`. GraphQL names a bot without the `[bot]` suffix REST adds, so the GitHub adapter asks for each author's `__typename` and names a `Bot` author `name[bot]`. `botKey` gives the repo's `trusted_bot` the suffix when it was stored without one. So a user account with the bot's bare name never matches the bot. Whole keys are compared, so a login that only starts with a trusted one never matches either (issue #79). Nothing marks a summary answered, so it comes back in every address round until its reviewer approves or reviews again, and the addresser's PR comment answering it doesn't come back with it. The address prompt says so: a standing summary may already be dealt with, so the addresser checks the code before changing anything for it. The bot's comments are the addresser's earlier replies. They came from a brief that held only trusted text, and without them a second round would see a reviewer's follow-up but not the reply it answers. The engine gives the addresser that list and nothing else from the PR, so an untrusted comment never reaches its brief.
11. **Policy files.** The factory hard-codes no quality criteria. Spec §6 "Policy files" defines five files: `dor.md`, `scenarios.md`, `pr-review.md`, `risk.md` and `dod.md`.
    - **Loading.** The factory reads them from the repo's `.factory/` at the run's pinned `config_sha`. Readiness has no run yet, so it reads the default branch head. A read that returns 404 means the file is absent. Any other read error throws, and the step retries on its next turn. A read error never falls back to a default.
    - **Defaults.** An absent file falls back to `$FACTORY_POLICY_DIR/<name>.md`, except `dod.md`, which has no default. A `Policy.sha` is the SHA-256 of its raw text, whether it came from the repo or a default, so a changed default counts as a policy change. Both images copy the factory's `policy/` folder to `/app/policy`, which is the default value of `FACTORY_POLICY_DIR`. A repo file replaces its default whole.
    - **Criteria.** Only `dor.md`, `pr-review.md` and `dod.md` have criteria, one per top-level `- [ ]` line, numbered from 1 in file order. The judge answers one JSON line per criterion: `{"index","status","reason"}`, where `status` is `passed`, `failed` or, in `dod.md` only, `person`. `person` means the line can only be met by a person or after merge, such as "deployed to staging". It goes to the PR checklist unticked and never counts as a fail. A missing index fails, and when an index appears twice, a fail wins. `scenarios.md` and `risk.md` are guidance, given whole to the agent that uses them.
    - **Commands.** A criterion holding `` `run: <command>` `` is allowed only in `dod.md`. `loadPolicy` rejects it in any other file with `PolicyError`. The cell runs `dod.md` commands at the end of green, in the checkout, as `execFile("sh", ["-c", command], { cwd, timeout: 900_000, env: { PATH, HOME, CI: "true", FACTORY_PG_BIN, ...proxy } })`, where `proxy` is the four proxy variables and `NO_PROXY` in both cases when the cell has them (Run contract 5). `FACTORY_PG_BIN` is the image's path to the Postgres binaries, so `startTestDb` can start a server in the command (PBI 22, Global Constraints). It is passed only when the image sets it. Without the proxy variables a command that needs the network, such as `npm ci`, fails locally. That env carries none of the cell's tokens. It isn't a sandbox, though: the command runs as the cell's own user, as `commands.test` does and as the agent does. So it has no more reach than the agent that wrote the code already has. The `bdd.*` and `commands.*` lines in `config.yml` run the same way, through `sh -c` in the checkout, so they may use shell syntax such as `VAR=value` and `$(...)`. A cell's clone has none of the repo's dependencies, so `commands.setup`, when set, runs once per cell after the base merge and before any stage, and a non-zero exit blocks the run with its output. This repo's is `npm ci`. Without it, a cell that resumes past green runs its first gate command with nothing installed.
    - **Fresh DoD.** Self-review and address can push code after green, and CI may not run a `run:` line such as `run: npm run e2e`. So each `dod.md` verdict records the commit it was checked at, in `policy_result.checked_sha`. Open-pr, and address before it posts `pr_opened`, check `dod.md` again whenever `git.head()` differs from `ctx.dodCheckedSha`, or the verdicts at that commit hold a failed line, so a retry that leaves HEAD where it was still gets checked. A failed line found there sends open-pr back to green, counted against green's retries, and counts as a failed address attempt. The PR checklist names the commit its verdicts were checked at.
    - **Results.** Every result is stored in `policy_result`, with `source` set to `repo` or `default`. The control plane writes readiness rows itself, and the cell sends its rows through `POST /policy-results` (Task 12).
    - **Re-gating.** `readinessSha(texts)` (Task 9) is the SHA-256 over every file the readiness check reads: the five policy files and `.factory/config.yml`. Each file contributes its raw text as read, or the default's text when the repo has none, prefixed with its length in UTF-8 bytes and a colon, so no text can slide across into the next file. A missing `dod.md` or `config.yml` contributes `-;`, which no length prefix starts with, so it never matches a file holding the word `absent` (PBI 21). Raw text means a file that fails to load, such as a `pr-review.md` with a `run:` line, still counts, and fixing it changes the hash. `item.readiness_policy_sha` records the value from the item's last check. The factory's own readiness logic follows the six files, length-prefixed the same way: the judge's prompt, which is `judgePrompt`'s words around an empty item and a `dor.md` with no text and one empty criterion, so the per-criterion line counts too, `READINESS_VERSION` from `src/policy/policy.ts`, and the split prompt, which is `splitPrompt`'s words around an empty item with one empty criterion and `TEMPLATE_DOR`, the same stand-in `dor.md` with no text and one empty criterion (PBI 159, PBI 202). Raise that version by one with any change to the engine rules (PBI 149). When the sha changes, because a team fixed any of those files, a deploy changed a default, or a deploy changed the judge's prompt or the split prompt or raised the version, the poller re-runs the gate on the item. An item in a repo the factory doesn't know gets a sha over the logic alone, so a logic change re-checks it too.
    - **Engine rules.** The rules no policy file can weaken are the list under "What stays in the engine" in spec §6. They live in code and prompts that the factory owns.
